00

开场：怎么把这个项目讲出去面试前 30 秒定生死：先给脚本，再谈细节

30 秒 · 电梯版

自制蓝牙音响，从原理图、双层 PCB、打样焊接到固件全部独立完成。ESP32 双核分工：Core 0 跑 A2DP 蓝牙音频和 I2S 输出，Core 1 跑 240×240 屏幕渲染，音频能量实时驱动"磁流体"动画。用 8 bit 色深把全屏缓冲从 115 KB 压到 58 KB，实测约 20 FPS。解决过初始化顺序导致的堆不足和蓝牙空闲爆音；功放底噪定位到供电与地回路，有改善未根治，停在验证版。

角色边界：个人项目，软硬件全部一人完成——这句话本身就是卖点，但要准备好被深挖任何一层（PCB 怎么画的、为什么选 PCM5102A、底噪怎么查的）。
2 分钟 · STAR 版

S｜想做一台"声音看得见"的桌面音响——音频流和图形渲染都是"必须准时"的任务，挤在一个核上会互相拖死。T｜整机自制：蓝牙配对播放、屏幕实时跟着音乐动、晃动机身有物理反馈、静置自动进待机。A｜四个关键决策：①双核边界——Core 0 归协议栈（A2DP + I2S），Core 1 归渲染主循环，两边只通过一个 256 点样本缓冲和一个标志位交互，零锁；②音频能量提取不做 FFT——256 样本按时域切三段求平均绝对值，一阶平滑后驱动动画，算力留给渲染；③8 bit 色深——全屏 Sprite 从 115 KB 降到 58 KB，避免和蓝牙协议栈抢堆内存；④用功放的 XSMT 静音引脚做"没声音就真关功放"，消除空闲底噪和起停爆音。R｜焊通可正常播放，音频到视觉链路完整，约 20 FPS；底噪经去耦和 RC 滤波有改善但未达标——主动交代，并说清排查路径。

讲法提醒这是五个项目里唯一的全栈个人项目——面试官问"独立完成到什么程度"时，从"嘉立创 EDA 画双层板"讲到"FreeRTOS 双核任务绑定"，跨度本身就是回答。别忘了主动揭底噪这个短：它反而证明你摸过模拟层。
01

两个核怎么不打架先建立整体印象：两条"必须准时"的流水线 + 一个共享缓冲

整台机器只有两条时间敏感的流水线：音频流（节奏由蓝牙包决定，慢一拍就是断音）和渲染流（节奏由帧率决定，慢一帧就是卡顿）。全部设计就是一句话——让它们各占一个核，只共享一个 256 点的样本缓冲。

从数据看

输入三路：蓝牙音频（A2DP）、MPU6050 六轴、（间接的）时间。输出两路：I2S 数字音频、SPI 屏幕刷新。所有代码都在搬运这五个量。

从并发看

两个核各自跑 FreeRTOS 任务，唯一的交界是一段缓冲 + 一个 volatile 标志。没有锁、没有队列、没有信号量——因为数据流向是单向的。

从节奏看

音频回调约每 5.8 ms 攒满 256 样本；渲染帧 50 ms（20 FPS）。音频比画面快近 10 倍——所以缓冲永远是最新的，掉几段分析也没人看得出来。

一、全景数据流

为什么这样分核ESP32 的 A2DP 协议栈必须在 Core 0（蓝牙控制器固定绑定）——所以"音频在 0、渲染在 1"不是自由选择，是唯一解。真正自由的决策是：渲染放 loop（默认 Core 1）而不是另开任务——渲染是唯一的周期性大户，独占主循环反而省掉了任务切换开销。

两个核共享 sampleBuf，为什么不加锁？

数据是单向、可丢弃的：Core 0 只写、Core 1 只读；读到的哪怕是一半新一半旧，也只是某一帧动画的能量略怪，下一帧就自我纠正。锁的价值是保护"不可接受的中间态"，这里不存在这种状态。知道什么时候不需要锁，比会加锁更难得。

02

硬件链路与引脚文件头注释就是接线表

整机三条链路：音频链（蓝牙 → I2S → DAC → 功放 → 喇叭）、显示链（SPI 刷屏）、传感链（I2C 读六轴）。每条链的接口协议都是为"数据量 × 实时性"选的。

  • "磁流体"是屏幕上的视觉，不是实物腔体——讲项目第一句就要说清，不然面试官以为你做了磁铁装置（文件头之外、README 里也该有这句）。

SPI 刷屏带宽怎么估？

240×240×1 字节 = 57.6 KB/帧；20 FPS 就是 1.15 MB/s ≈ 9.2 Mbps——SPI 时钟 40 MHz 绰绰有余，瓶颈不在总线，在逐像素画圆的 CPU 时间（第 09 节展开）。

03

音频回调与静音audioDataCallback · Core 0 上每 5.8 ms 被叫醒一次

这个回调干三件事：把立体声混成单声道塞进环形缓冲、攒满 256 点举旗、顺手解除功放静音。它跑在蓝牙协议栈的上下文里——写得越长，音频延迟越大。

一、缓冲区的三个声明

Sandspeaker.ino26–35 音频缓冲与静音
// ── 音频分析缓冲 ──────────────────────────
#define SAMPLE_SIZE 256
int16_t  sampleBuf[SAMPLE_SIZE]; ①
volatile int  sampleCount = 0;
volatile bool newSamples  = false; ②

// ── XSMT 静音控制 ─────────────────────────
#define PIN_XSMT 14
volatile bool btPlaying   = false; ③
uint32_t      lastAudioTime = 0;
  • sampleBuf 本身没有 volatile——但它跨核读写！能侥幸工作的原因：ESP32 两核共享 DRAM 且 cache 一致，写侧是顺序追加、读侧只在"攒满"标志置位后才整体读。严谨做法是整个缓冲都 volatile 或加内存屏障；这里编译器恰好没做导致破坏的重排（推断）。面试时主动指出"我知道这里差一口气"。
  • sampleCount 和 newSamples 是 volatile：单写多读的"进度指示牌"。volatile 保证 Core 1 每次都真去内存读它，而不是用寄存器里的旧值。
  • btPlaying / lastAudioTime 分属两个核写：回调里写（Core 0），loop 里读并写（Core 1）。bool 和 32 位对齐字的读写各自原子，最坏情况是"晚一拍静音"——无害。

二、回调逐行

Sandspeaker.ino112–126 音频回调
void audioDataCallback(const uint8_t *data, uint32_t len) {
  // 收到数据时解除静音
  if (!btPlaying) {
    digitalWrite(PIN_XSMT, HIGH); ①
    btPlaying = true;
  }
  lastAudioTime = millis();

  int16_t *samples = (int16_t*)data; ②
  int count = len / 4;
  for (int i = 0; i < count && sampleCount < SAMPLE_SIZE; i++) {
    sampleBuf[sampleCount++] = (samples[i*2] / 2 + samples[i*2+1] / 2); ③
  }
  if (sampleCount >= SAMPLE_SIZE) newSamples = true; ④
}
  • 解除静音放在最前面：功放从静音到工作要过渡时间，越早拉高，第一声越完整。这就是"上电默认静音、来数据才开"的前半句（后半句是 2 秒超时，见下）。
  • 把字节流强转成 int16 指针：A2DP 给的是 16 bit 立体声 PCM 的原始字节，每 4 字节 = 左右声道各一个采样。这个强转依赖小端和对齐——ESP32 上都满足。
  • 立体声混单声道：左右各除 2 再相加（等价于求平均，防溢出先除后加）。视觉不需要声场，单声道省一半分析量。
  • 攒满才举旗：count < SAMPLE_SIZE 的保护意味着缓冲满后多余样本直接丢弃——音频继续正常播（I2S 是独立通路），只是这一段没被分析。丢分析不丢声音，优先级摆得很清楚。

三、静音的另一半：2 秒超时

Sandspeaker.ino453–457 loop 内
  // 超过 2 秒没有音频数据自动静音
  if (btPlaying && millis() - lastAudioTime > 2000) { ①
    digitalWrite(PIN_XSMT, LOW);
    btPlaying = false;
  }
  • 读的是 Core 0 写的时间戳——又一个跨核共享量。32 位对齐字原子读写，最坏差一拍，无害。
  • 为什么用"读侧超时"而不是"停止事件"：A2DP 的暂停/断开没有可靠的"通知你一声"钩子，与其猜事件，不如看数据本身——2 秒没新数据 = 事实上的空闲。2 秒是歌曲间隙的上限估计（推断）。

爆音到底是怎么产生的？为什么 XSMT 能消掉？

功放输入端有一个直流偏置。开始/停止播放的瞬间，I2S 数据流突然出现/消失，输入直流跳变经放大后在喇叭上表现为"啪"一声（阶跃响应）。XSMT 把功放内部的偏置电路直接关断——不是把音量调到零，是让放大链路根本不存在，直流跳变无处可放大。要点：拉高要赶在第一段数据前（所以回调开头就做），拉低要等确认空闲（2 秒超时）。

04

三段能量：不是 FFTanalyzeAudio · 全项目最容易被追问"名不副实"的地方

变量叫 bassEnergy / midEnergy / highEnergy，但它们不是低中高频——是 256 个样本按时域顺序切的三段各自的整体能量。先把这件事说破，这一节的所有设计才立得住。

为什么必须先说破懂 DSP 的面试官一眼就能看出：5.8 ms 的窗口内按索引分段，不做变换，任何一段都包含全频段成分。变量名的"bass/mid/high"是视觉效果的名字，不是信号处理的名字。被问到"你这真是频谱吗"时，答"不是，是时域分段能量，我故意没上 FFT"——这一题答好了是全场加分最高的地方，答砸了是全场最尴尬的地方。

一、逐行读

Sandspeaker.ino131–158 能量分析
void analyzeAudio() {
  if (!newSamples) return; ①
  newSamples  = false;
  sampleCount = 0;

  float bass = 0, mid = 0, high = 0;
  int bassEnd = SAMPLE_SIZE / 8;      // 32
  int midEnd  = SAMPLE_SIZE / 2;      // 128

  for (int i = 0; i < SAMPLE_SIZE; i++) {
    float v = fabsf((float)sampleBuf[i]) / 32768.0f; ②
    if      (i < bassEnd) bass += v;   ③
    else if (i < midEnd)  mid  += v;
    else                  high += v;
  }

  bass /= bassEnd;                     ④
  mid  /= (midEnd - bassEnd);
  high /= (SAMPLE_SIZE - midEnd);

  bassEnergy = bassEnergy * 0.6f + bass * 0.4f * 4.0f; ⑤
  midEnergy  = midEnergy  * 0.6f + mid  * 0.4f * 3.0f;
  highEnergy = highEnergy * 0.6f + high * 0.4f * 3.0f;

  bassEnergy = constrain(bassEnergy, 0.0f, 1.0f); ⑥
  midEnergy  = constrain(midEnergy,  0.0f, 1.0f);
  highEnergy = constrain(highEnergy, 0.0f, 1.0f);
}
  • 没攒满就 return：渲染帧率 20 Hz，音频段率约 170 Hz——大多数帧进来时缓冲还没满，直接跳过。分析是机会性的，不是每帧必有，能量靠平滑保持连续感。
  • 取绝对值再归一化到 0–1：除以 32768（int16 满量程）。不取绝对值的话正负抵消，安静的音乐和响的音乐都会算出接近 0。
  • 三段切分比例是 1/8 : 3/8 : 1/2（32 : 96 : 128 点）。三段分别对应 0.73 ms / 2.2 ms / 2.9 ms 的子窗。鼓点这类瞬态能量集中在窗的前段（新数据刚进来），所以前 1/8 给了最高的增益（×4）——比例和增益是视觉调出来的（推断），不是理论推导的。
  • 三段长度不同所以要分别除以各自长度：算的是平均幅度，否则长的那段天然数值大。
  • 一阶低通：旧值 0.6 + 新值 0.4。等效时间常数：每段约 5.8 ms 一次更新，0.6 的保持率 → 约 15 ms 的平滑窗。不滤波的话画面会跟着每个音频包乱跳，"看起来像坏了"。
  • 钳到 0–1：增益 ×4/×3 可能把值顶过 1，钳位让下游映射（半径、配色）永远拿到合法输入——和 PIC 小车控制律的输出限幅是同一个思想：出口必须有栅栏。

二、那"跟着鼓点动"是错觉吗？

是半错觉，而且是设计出来的好错觉。三段时域能量能反映的，是这 5.8 ms 窗口的包络起伏：鼓点来的时候整体幅度猛涨，bassEnergy（窗前段）涨得最快；镲片高频为主的段落整体幅度小但起伏密。听感上"低频 = 鼓"的关联，来自音乐的编曲规律（鼓点往往伴随整体振幅峰值），不是来自频率分离。所以它在大多数流行乐上"看起来很准"，在纯人声清唱上会"不动"。诚实地讲出这个边界，比硬说它是频谱分析可信一百倍。

为什么不上 FFT（面试必问，先算账）： 256 点 FFT ≈ 每次几千次浮点乘加（ radix-2 蝶形） 一帧 50 ms 里就算只做一次，也要抢渲染 10%+ 的预算（推断） 而三段能量 = 256 次 fabs + 加法，不到 FFT 的 1/20 结论：视觉只需要三个随音乐呼吸的数，不需要 128 条频带 ——"没做"是预算决策，不是能力缺口

如果要真·频谱，最小改动怎么做？

ESP32 有现成的 DSP 库（esp-dsp 的 FFT），256 点实数 FFT 微秒级——在 ESP32-S3 上甚至有向量指令。改动：analyzeAudio 里把三段求和换成 rfft + 取 3–4 个频带的幅值。但注意 A2DP 回调的采样率是 44.1 kHz，256 点只覆盖 172 Hz 的频率分辨率——想分出低音鼓（60–120 Hz）得加长窗口到 1024 点，延迟和算力一起涨。能讲出"分辨率 = 采样率 ÷ 窗长"这一层，问题就闭环了。

05

渲染引擎与液滴触角、核心球、发光环、30 颗液滴——全是"算出来的"圆

画面上没有任何素材图：五条触手 + 核心球 + 三层发光环 + 30 颗液滴，全是用 sin/cos 和 fillCircle 画出来的圆。动画的秘密只有一个——每个参数都有一个"目标值"，每帧向目标挪一小步。

一、物理更新：目标值 + 缓动

Sandspeaker.ino188–217 updatePhysics 节选
void updatePhysics() {
  uint32_t t = millis();

  ringRadiusTarget = 88.0f + bassEnergy * 18.0f; ①
  ringRadius += (ringRadiusTarget - ringRadius) * 0.12f;

  ringColorPhase += midEnergy * 0.008f + 0.002f; ②
  if (ringColorPhase > 1.0f) ringColorPhase -= 1.0f;

  coreRadiusTarget = CORE_R_BASE + bassEnergy * 12.0f;
  coreRadius += (coreRadiusTarget - coreRadius) * 0.18f; ③

  for (int i = 0; i < NUM_ARMS; i++) {
    float noise =
      sinf(t * 0.004f + armPhase[i]) * 0.6f +
      sinf(t * 0.009f + armPhase[i] * 1.7f) * 0.4f; ④

    armAngleTarget[i] = (float)i / NUM_ARMS * 2.0f * M_PI
                        + noise * 0.35f
                        + t * 0.0003f;
    armAngle[i] += (armAngleTarget[i] - armAngle[i]) * 0.06f; ⑤

    float distNoise = sinf(t * 0.006f + armPhase[i] * 2.3f) * 0.3f + 0.7f;
    armDist[i] = ARM_DIST_BASE * distNoise + bassEnergy * 22.0f; ⑥

    float sizeNoise = sinf(t * 0.015f + armPhase[i]) * 0.2f + 0.8f;
    armRadius[i] = ARM_R_BASE * sizeNoise + bassEnergy * 8.0f;

    armPhase[i] += 0.002f;
  }
}
  • 三段能量各管一摊：低段驱动环半径（88±18）、核心球（28±12）、触手伸展（+22）；中段驱动配色相位；高段只在液滴上体现。低段给了最多的自由度——因为窗前段对鼓点瞬态最敏感，视觉上"整个身体跟着鼓点呼吸"。
  • 配色相位永远在走：+0.002 是底速（静止音乐时环也慢慢变色），midEnergy ×0.008 是音乐加速——没音乐也不能死气沉沉，这是"待机感"和"死机感"的区别。
  • 不同缓动系数 = 不同手感：环 0.12、核心球 0.18、触手角度 0.06——核心球跟得最紧（离中心近、变化要显），触手最迟钝（越远的肢体惯性越大）。单一系数会让整个形态像刚性物体整体缩放，三个系数让它像流体的不同粘度层。
  • 两个不同频率的 sin 叠加当噪声：0.004 和 0.009 两档频率、0.6/0.4 权重——比单个 sin 复杂、比随机数平滑，是最便宜的"伪有机运动"。
  • 触手角度直接带缓动：目标角每帧都在变（噪声 + 0.0003×t 的慢速整体旋转），当前角以 0.06 的步长追——触手甩动就是这么来的。
  • bassEnergy 直接加在距离上（×22）而角度走缓动——距离是"音量推出去"，角度是"自己慢慢晃"，两种节奏叠出触手的摆动。

为什么用全屏 Sprite 双缓冲，不直接往屏幕画？

一帧要画几百个圆，直接上屏的话每画一个圆用户就看见一次中间态——液滴满天飞的同时触手在闪，像撕裂。Sprite 先在内存里画完整帧，一次 push 到屏幕：观众永远只看到完成的帧。代价是那块 58 KB 的缓冲——这正是 8 bit 色深决策的由来（第 07 节）。

fillCircle 一帧要调几百次，瓶颈在哪？

每个 fillCircle 内部是逐行画水平线段，像素级的内存写。粗算：环 5 层 + 颈部 ~15 圆 × 5 触手 + 核心球 + 液滴 ≈ 每帧写入约 5–6 万像素 = 57.6 KB 的全屏缓冲要重写一遍——50 ms 的帧预算里渲染占了大头。所以 20 FPS 的第一优化方向不是 SPI 带宽，是减少重绘面积（局部刷新）。

06

静止检测与待机加速度计当"存在传感器"用，0.03/0.08 的不对称渐变

设备静置 2 秒 → 平滑过渡到"呼吸球"待机画面；一晃就切回磁流体。切换不是 if-else 的硬切，是一个 0→1 的插值系数在双向爬坡——而且爬上去和滑下来的速度不一样。

Sandspeaker.ino434–451 loop 内

  • 静止 = "两帧之间重力方向几乎没变"：gDelta 是相邻两帧重力读数的 L1 距离。阈值 0.08——小于它就算"没在动"。比"绝对值小于阈值"更鲁棒：拿起设备匀速平移时绝对值会变，但相邻帧差值依然小（会被误判为静止，这是个已知边界，好在演示场景不涉及）。
  • 2 秒确认（STILL_DELAY）：和 FPGA 圈数计数的 15 ms 确认是同一个模式——状态切换前先持续一段时间，防抖动的时域版。stillStartTime 在每次"动了"时刷新，静止判定自动顺延。
  • 不对称速率：进待机 0.03/帧、退出 0.08/帧。20 FPS 下进待机要 ~1.7 s、退出只要 ~0.6 s。从静到动要快（用户已经动了，画面不能装死），从动到静要慢（谁也不想一个刹车就变成呼吸球）。交互手感就藏在这种不对称里。

为什么用加速度计检测"动"，不用陀螺仪角速度？

手里拿设备晃是以平动为主的扰动，加速度计的相邻帧差对它最敏感；陀螺仪对旋转敏感但对"整体平移"不敏感。而且 gravX/gravY 本来就要读（液滴要重力方向）——一个传感器复用两个用途：重力向量 + 活动检测，零额外成本。

07

内存：8 bit 的取舍全项目最重要的一次"省"：115 KB → 58 KB

ESP32 的 DRAM 要养三方：蓝牙协议栈、WiFi（共存时）、和你的帧缓冲。16 bit 全屏 Sprite 是 115 KB，8 bit 只要 58 KB——差出来的 57 KB 决定了蓝牙能不能启动。

一、账本

240 × 240 = 57600 像素 16 bit 色深：57600 × 2 = 115200 B ≈ 112.5 KB 8 bit 色深：57600 × 1 = 57600 B ≈ 56.3 KB 省下 56.3 KB——ESP32 可用堆总共约 300 KB 量级， 蓝牙 A2DP 一启动就要吃掉一大块连续内存 → 16 bit 时：Sprite 申请失败或蓝牙起不来（实测崩溃） → 8 bit 时：两者共存，还有余量

二、8 bit 色深怎么用

三、初始化顺序：一次真实的崩溃与修复

踩坑记录（简历可讲的原版故事）最初顺序是"先蓝牙后 Sprite"：A2DP 协议栈启动时吃掉一大块堆，剩下的内存碎了——Sprite 需要 56 KB 连续内存，碎片里拼不出来，createSprite 失败，程序崩。修复：调转顺序——先把最大的一块连续内存占住（Sprite），再让蓝牙去用剩下的。同时养成习惯：每个关键节点打印 ESP.getFreeHeap()。大块分配要趁早，这是嵌入式内存管理的第一课。

四、代价清单

维度16 bit（RGB565）8 bit（本项目）

色彩65536 色，渐变丝滑256 色调色板，大渐变会出现色带（banding）

除了降色深还有什么路？

按省的量排：①局部刷新——只 push 变化区域，但液滴满屏跑，脏区接近全屏；②减分辨率——Sprite 画 120×120 拉伸上屏，内存直接 ÷4，代价是糊；③换带 PSRAM 的模组——帧缓冲挪出主 RAM，代价是 BOM 和 push 带宽。选 8 bit 是"不动架构、代价可控"的那一刀。

怎么知道内存是"碎"了而不是"没了"？

看两个数：ESP.getFreeHeap()（还剩多少）和 ESP.getMaxAllocHeap()（还能分配的最大连续块）。free 有 80 KB 但 maxAlloc 只有 30 KB，就是典型的碎片——够总数不够连续。把两个都打印，才是完整的仪表盘。

08

一帧的生命loop() 逐行推演 + 50 ms 帧预算怎么花掉的

每 50 ms（20 FPS）跑一遍 loop，顺序是：读传感器 → 判静止 → 查静音超时 → 分析音频 → 更新物理 → 更新液滴 → 清屏重画 → push → 打印 FPS。顺序本身就是依赖关系图。

① mpu.getEvent（阻塞 I2C 读）

一次事务读 14 字节，约 1 ms 量级。拿到重力向量 → 刷新 gravX/gravY、gDelta、deviceStill、stateTransition。液滴的"下落方向"在这里就定了。

② XSMT 超时检查

2 秒没音频就拉低静音（第 03 节）。放在渲染前——渲染花的时间也算进"下一帧的 2 秒"里，逻辑不乱。

③ analyzeAudio（可能空手而归）

缓冲没满直接 return；满了就算三段能量 + 平滑。约 170 Hz 的段率对 20 Hz 的帧率——大约 8 次里 7 次是空转，真正的计算被摊得很稀。

④⑤ updatePhysics / updateDroplets

纯内存运算，浮点乘加几百次——微秒级，忽略不计。所有"目标值→缓动"的推进发生在这里。

⑥ fillSprite + 渲染三选一

先整帧清黑，然后 stateTransition > 0.95 画呼吸球，否则画环 + 流体；液滴最后叠加（在最上层）。这一步是大头：几百个 fillCircle，写穿整块 58 KB 缓冲。

⑦ pushSprite

58 KB 走 SPI 到屏幕。总线 40 MHz 时传输只要 ~12 ms，但与渲染 CPU 时间部分串行——渲染 + 推送一起吃掉 50 ms 里的大部分（推断）。

⑧ FPS 统计

每秒打印一次帧率和三个能量值——运行时的"体检报告"。串口开着的时候，性能问题无处藏身。

帧预算（推断，量级）

I2C 读 ≈1 ms · 分析 ≈0（摊薄）· 物理/液滴 <1 ms · 渲染 ≈20–30 ms · push ≈10–15 ms → 合计贴近 50 ms 上限。所以 20 FPS 是渲染画圆画出来的瓶颈，不是总线也不是蓝牙。

loop 里没有 delay

帧率是"跑多快算多快"，不是定时器节拍。真跑 22 FPS 也不影响任何逻辑——所有时间相关量都基于 millis() 自己算。无阻塞、无固定节拍，与 PIC/FPGA 项目的时间纪律一脉相承。

一个可以背的口径问"你这 20 FPS 怎么测怎么优化的"：FPS 是每秒串口打印的实测值；优化优先级是减少重绘面积（脏矩形）> 降色深到 4 bit > 提高 SPI 时钟——第一项收益最大，因为瓶颈在逐像素画圆不在总线。

底噪战争与边界一个未解决的问题，和几个"差一口气"的地方

数字部分全部跑通之后，功放底噪成了整机不可用的最后一道墙。这一节是这个项目最值钱的部分——因为它证明了"代码写对"和"东西能用"之间隔着模拟那一层。

一、底噪排查（按实际操作讲）

现象

播放中能听到持续的"沙——"底噪；蓝牙空闲时已被 XSMT 消掉，但一放歌底噪就跟着出现——它乘着音频通路进来的。

第一步：断音源

断开蓝牙只开机——XSMT 静音生效，没噪声。结论：噪声源在"播放态"的模拟链路里，不是功放自激。

第二步：换供电

电池 vs USB 对比（按实际讲）——底噪有变化，指向电源纹波耦合。

第三步：两件事处理

①电源去耦：功放供电脚附近加电容，压纹波；②RC 低通：音频输入端加阻容，滤高频干扰。

追问链：嵌入式岗最常挖的三条线

链 A：从 volatile 挖到内存模型

  1. L1"哪些变量加了 volatile？为什么？"——sampleCount / newSamples / btPlaying：跨核共享的进度与状态，防编译器把它缓存进寄存器。
  2. L2"sampleBuf 为什么没加？加了会怎样？"——没加是侥幸：靠 ESP32 cache 一致和编译器没做破坏性重排。加了会阻止向量化优化（这些操作也没向量化，损失不大），正确姿势是读写屏障或干脆用 FreeRTOS 流缓冲区。
  3. L3"volatile 和原子性什么关系？和 cache 什么关系？"——volatile 只管编译器可见性，不管原子性（多字节撕裂）也不管核间 cache 一致（那是 MESI 协议的事）。C++11 之后正确工具是 std::atomic + memory_order。能分清这三层，这条线就到头了。

链 B：从帧率挖到性能方法论

  1. L1"20 FPS 怎么来的？"——每秒串口打印 frameCount，实测。
  2. L2"怎么知道瓶颈不是蓝牙不是总线？"——隔离变量：蓝牙在另一个核（排除）；把渲染注释掉只 push，帧率飙升（锁定渲染）。三分钟两步，比猜快。
  3. L3"还有更系统的工具吗？"——有：ESP-IDF 的性能追踪（tracealyzer 类）、GPIO 翻转 + 示波器量每段耗时、或在每步前后打 micros() 做软计时。我这个项目用的是打点 + 隔离实验——够用，且能讲清为什么够用。

链 C：从"个人项目"挖到工程化短板

  1. L1"一个人做的，怎么保证代码是对的？"——分层验证：串口打印（能量/FPS/堆）是运行时护栏；每个模块独立可测（分析器喂假样本就能跑）。
  2. L2"有什么是团队项目才教你的？"——接口管理和别人的依赖：气体检测项目里我做的采样单元要交给化学组用，异常分支比功能更早设计——这个习惯个人项目练不出来。
  3. L3"这个项目如果量产，还缺什么？"——EMC、热设计、结构（外壳/腔体）、产测、固件 OTA……能列出这张清单本身就是答案：知道自己没做过的边界在哪。

12 条

  • ■ setColorDepth 必须在 createSprite 之前——缓冲大小创建即定，之后改色深不生效。
  • ■ 大块堆分配要趁早：先起蓝牙再建 Sprite = 碎片里拼 56 KB 连续块，必崩。顺序反过来就活。
  • ■ 监控内存要打两个数：getFreeHeap()（总量）+ getMaxAllocHeap()（最大连续块）——只看总量会把碎片当成"还有余量"。
  • ■ volatile 只管可见性：不保证原子、不保证顺序。跨核多字节共享要么原子要么加保护。
  • ■ A2DP 回调跑在协议栈上下文里——里面只做搬运不做计算，越短音频延迟越小。
  • ■ 立体声混单声道要先除后加：直接相加 16 位会溢出回绕，轻则削顶重则相位反听感。
  • ■ 能量不取绝对值 = 正负抵消：响音乐和静音都会算出接近零，动画死掉。
  • ■ 视觉驱动链的出口必须有钳位：增益会把能量顶过 1，没有 constrain 半径会算出负数或巨值。
  • ■ ESP32 的 loopTask 固定 Core 1、蓝牙固定 Core 0——"双核怎么分"的答案一半是芯片定的，别揽功。
  • ■ int16 强转字节流依赖小端与对齐——换平台前先确认，别让"能跑"骗过去。
  • ■ 嵌入式不用链表不用 new：液滴用定长数组对象池，碎片纪律从第一行开始。
  • ■ UI 状态切换要渐变、渐变要不对称：唤醒快、入睡慢——手感差异全在这 0.05 上。

自测 8 题两道必须动笔算，一题必须能推演

答案默认折叠。先写下来再展开——第 1、2 题是数字账，被现场问到的概率最高。

【算】256 点样本在 44.1 kHz 采样率下代表多长的窗口？三段各占多少毫秒？

窗长 = 256 ÷ 44100 ≈ 5.8 ms 前段 32 点 ≈ 0.73 ms（鼓点瞬态最敏感） 中段 96 点 ≈ 2.18 ms 后段 128 点 ≈ 2.90 ms

【算】240×240 的帧缓冲，16 bit 和 8 bit 各多少 KB？8 bit 省下的字节能干什么？

16 bit：57600 × 2 = 112.5 KB 8 bit：57600 × 1 = 56.3 KB 省 56.3 KB——实测 16 bit 时蓝牙协议栈与帧缓冲不能共存（堆被切碎）， 8 bit 让两者共存且 SPI 推屏带宽减半

bassEnergy 的更新式是"旧值×0.6 + 新值×0.4×增益"。分析更新率约 170 Hz 下，这个平滑的等效时间常数大约是多少？为什么需要它？

每步保留 0.6，衰减到 1/e（≈0.37）需要 n 步满足 0.6ⁿ = 0.37 → n ≈ 2 拍，约 12 ms。不滤波的话能量跟着每个音频包猛跳（170 Hz 的抖动），画面会像坏掉；12 ms 的平滑让鼓点"打进来、慢慢泄掉"，视觉上是脉动不是闪烁。

为什么 sampleBuf 不加锁是安全的？说出"无锁三条件"，并各对应到本项目。

①单写者——只有 Core 0 的回调写缓冲；②单读者——只有 Core 1 的 analyzeAudio 读；③数据可丢弃——读到撕裂的半帧只是某帧动画能量略怪，下一帧自愈，没有"不可接受的中间态"。三者任一不满足（比如两个任务都写）就必须上互斥或环形队列。

如果面试官说"你这 bass/mid/high 就是频谱分析吧"，你怎么接？

主动纠正：它是 5.8 ms 窗口内按时域顺序切的三段整体能量，任何一段都含全频段成分。它看起来"跟低频走"是编曲规律（鼓点伴随整体振幅峰值）造成的包络关联。不上 FFT 是渲染算力的取舍；真要频谱，256 点窗的分辨率只有 44100/256 ≈ 172 Hz，分鼓点得加窗到 1024 点。

XSMT 的拉高为什么写在回调最开头？拉低为什么用 2 秒超时而不是"暂停事件"？

拉高要赶在第一段音频数据到达 DAC 之前——功放开起来有过渡时间，晚了第一声就缺。拉低不看事件是因为 A2DP 没有可靠的暂停/断开钩子，"2 秒没有新数据"是唯一可靠的事实判定（读侧超时模式）；2 秒取的是歌曲间隙上限的量级。

渲染帧 50 ms、音频段率 170 Hz——为什么大多数帧的 analyzeAudio 是空转？这样设计对不对？

渲染 20 Hz、缓冲攒满 170 Hz——大约 8 次循环里 7 次缓冲还没满，newSamples=false 直接 return。对：分析是"机会性消费"不是"每帧义务"，丢掉的分析段对视觉无感（有平滑兜底），而如果反过来让渲染等分析，音频节奏会绑架帧率。设计原则：快的生产者、慢的消费者，天然要允许丢弃。

【推演】把 setup() 里"先 Sprite 后蓝牙"改回去（先蓝牙后 Sprite），完整描述会发生什么、怎么定位。

发生：A2DP 启动吃掉一大块堆并把剩余堆切碎 → createSprite 要 56 KB 连续块，getMaxAllocHeap() 不够 → createSprite 返回 nullptr 或断言崩溃，黑屏。定位：串口打印 free/maxAlloc 两个数——free 显示还有几十 KB 但 maxAlloc 只有零头，即外部碎片；再用注释法二分（注释蓝牙启动看 Sprite 是否成功）确认因果。修法：恢复顺序，并在 README 记下"大块分配要趁早"。
