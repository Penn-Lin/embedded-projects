2 KB 内存教会我的事

Arduino UNO（ATmega328P）· OLED 128×64 + 无源蜂鸣器 + 四按键 · 大一第一个"从选型到成品"的个人项目

这不是技术最难的项目，但它把"内存布局"从课本名词变成了手上的事故：花屏、随机复位、然后是把 1024 字节搬进 Flash 的那一次豁然开朗。

00

开场：怎么把这个项目讲出去它是成长线的起点——讲"启蒙"，不讲"难度"

30 秒 · 电梯版

大二的个人项目：128×64 OLED + 无源蜂鸣器 + 四按键的小装置，两套"算出来的"动画（五角星、正弦波红旗）、三首乐谱非阻塞播放、四级按键优先级，双 18650 带保护板供电。核心收获是解决了一次真实的 2 KB SRAM 溢出——把全屏位图和乐谱全部移进 Flash，第一次真正理解 AVR 的双地址空间。

角色边界：纯个人项目，硬件选型、供电设计、软件全部一人。它是五个项目里最"轻"的，但面试里有两个不可替代的考点：PROGMEM 的原理和非阻塞编程的第一次实践。
2 分钟 · STAR 版

S｜想做一台能脱离电脑跑的桌面小装置——供电、交互、显示、声音四件事从零拼。T｜四按键各司其职：总开关、切动画、切曲、显示全屏徽章位图；动画与音乐同时进行互不打断。A｜三个关键点：①所有长时序逻辑非阻塞化——音乐靠"到点取下一个音符"、动画靠逐帧重绘，主循环永远不被 delay 卡死；②动画不贴素材，五角星用三角函数算顶点（内半径取 0.382 的标准五角星比例）、红旗用逐列正弦偏移；③爆内存之后把位图与乐谱全部 PROGMEM 进 Flash，读取改用 pgm_read_word / drawXBMP。R｜四按键、两动画、三曲、一位图全部稳定运行，脱离 USB 独立供电工作。复盘时发现第三首乐谱漏加了 PROGMEM——还留在 RAM 里，恰好能讲"为什么 code review 要看存储修饰符"。

讲法提醒这个项目的正确打开方式是当"起点"讲：它是后面所有项目的地基——非阻塞的习惯（PIC、气体检测都在用）、"先想异常"的意识、对内存的敬畏（ESP32 的 8 bit 决策从这里长出来）。单独吹它的技术深度会露怯，放进成长线里它就是必不可少的第一块砖。
01

一个 loop 的非阻塞骨架先建立整体印象：四件事轮转，谁都不许赖着不走

整个系统就是一个大轮询：扫按键 → 按优先级改模式 → 按模式画画面 → 到点取下一个音符。没有中断、没有 RTOS——但同样做到了"动画和音乐同时跑"，靠的只有一条纪律：任何一步都不阻塞。

从状态看

一个总开关 systemActive、一个徽章模式 badgeMode、动画号和曲目号——四个变量就是全部"操作系统"。

从时间看

三个节奏并存：动画每 30 ms 一帧（loop 尾的 delay(30)）、音符各 250–1200 ms 自己的时长、按键 50 ms 节流。时间不归 loop 管，归 millis() 管。

从内存看

2 KB SRAM 要养：U8g2 全屏缓冲 1 KB + 位图 1 KB + 曲谱 + 栈——正是这个挤爆了内存，第 08 节的战争现场。

FinalVersion…ino358–429 loop 全貌（节选）
void loop() {
  // 检测K1（系统总开关）
  if (checkButton(BUTTON_K1)) { ①
    systemActive = !systemActive;
    noTone(BUZZER_PIN);
    badgeMode = false;  // 强制退出徽章模式
    if (!systemActive) {
      u8g2.clearBuffer();
      u8g2.sendBuffer();
    }
    currentNote = 0;

  }

  if (!systemActive) return;  // 系统未激活时直接返回 ②

    currentNote = 0;
    previousMusicTime = millis();
    noTone(BUZZER_PIN);
    delay(300);
  }

  // K2动画切换
  if (checkButton(BUTTON_K2)) { ③
    animationMode = (animationMode + 1) % 2;
    currentNote = 0;
    u8g2.clearBuffer();
    xOffset = 0;
    waveOffset = 0.0;
    delay(300);
  }

  // K3 在徽章模式下被屏蔽 ④
  if (checkButton(BUTTON_K3) && !badgeMode) {
    soundMode = (soundMode + 1) % 2;
    ...
  }

  if (badgeMode) {
    drawBadge();
    playMeiyouGongchandang();
  } else {
    if (animationMode == 0) { /* 五角星 */ }
    else { /* 红旗 */ }
  }

  if (systemActive && !badgeMode) {
    handleMusic(); ⑤
  }

  delay(30); ⑥
}
  • K1 在 return 之前扫——关机后 loop 依然每圈扫总开关，否则关了就永远开不回来。先扫谁不是随便排的：能关掉一切的必须永远活着。
  • return 是"关机开关"：一句短路跳过后面所有逻辑，比到处写 if(systemActive) 干净。注意它跳过了 delay(30)——关机后 loop 空转得飞快，无害。
  • 每次模式切换都做三件事：清音符、清屏、重置动画参数——切模式 = 清状态，不清就串台（切到红旗时五角星的偏移还残留着）。
  • 四级优先级的"执行面"：K3 在徽章模式下直接不响应（条件里带 !badgeMode）——优先级不只是顺序，还是屏蔽。
  • 音乐是"顺路"的：主流程画完画面，handleMusic 检查"上个音符到时了吗"——到点取下一个，不到点立即返回。音乐不占用帧，帧也不等音乐。
  • delay(30) 是帧率节拍器：唯一"合法"的延时，因为它同时是所有动画的帧间隔。它也是这个骨架里最粗糙的一笔——真正的非阻塞该用 millis() 判帧（见易错点）。

这和 delay 写到底的版本有什么区别？

如果播音乐用 delay(音符时长)，一拍 500 ms 里屏幕完全冻结、按键全失灵。现在的版本里"等待"被摊薄成每帧 30 ms 的切片，任何任务的等待都 ≤30 ms——这就是非阻塞的全部意义：把"等"从"卡住"变成"过会儿再看"。

02

硬件：2 KB 的板子先把"资源饥饿"的舞台搭起来

ATmega328P：16 MHz、32 KB Flash、2 KB SRAM、1 KB EEPROM。对新手最反直觉的一件事：程序再大也有地方放（Flash 够），数据一多就爆（SRAM 只有 2048 字节）。

部件规格为什么这么选（/踩过什么）
OLED128×64，I2CU8g2 全缓冲模式需要 1024 B RAM——内存危机的另一半（第 08 节）
蜂鸣器无源有源给电就响只有一种音高；无源要外部方波，所以能奏乐（tone()）
按键 ×4内部上拉省元件；代价是上拉 20–50 kΩ 抗干扰弱——课桌环境够用
供电2×18650 串联 7–8.4 V过充过放保护板 + 降压到 5 V——第一次理解"电池/保护/降压"三段分工
先把最要命的账摆出来（第 08 节的主角）： 一张 128×64 位图 = 128 × 64 ÷ 8 = 1024 B U8g2 全屏显示缓冲 = 1024 B 乐谱（频率+时长，最大一首 30+30 个 uint16）≈ 120 B 三张账合计 ≈ 2168 B ＞ 2048 B —— 爆

为什么位图是 128×64÷8 字节？

单色屏每像素 1 bit：8 个像素打包成 1 字节。128 像素一行 = 16 B，64 行 = 1024 B。"位图的字节数 = 宽 × 高 ÷ 8"——这一除是嵌入式面试的单色屏送分题。

03

按键：防抖与优先级checkButton 的"节流式防抖"——一个值得自己拆穿的写法

四个按键要排队：总开关 > 徽章模式 > 动画切换 > 音效切换。高优先级按下时清掉低优先级的临时状态；低优先级在高优先级模式里直接失声。而防抖的写法——严格说它不是消抖，是节流，这是本节最值钱的一句话。

FinalVersion…ino288–304 按键检测
bool checkButton(int pin) {
  static unsigned long lastDebounceTime[4] = { 0 };
  const int debounceDelay = 50;
  int index = 0;
  if (pin == BUTTON_K1) index = 0;
  else if (pin == BUTTON_K2) index = 1;
  else if (pin == BUTTON_K3) index = 2;
  else if (pin == BUTTON_K4) index = 3;

  if (digitalRead(pin) == LOW) {
    if (millis() - lastDebounceTime[index] > debounceDelay) { ①
      lastDebounceTime[index] = millis();
      return true;
    }
  }
  return false;
}
  • 每个按键一个独立的时间戳（static 数组）——四个按键的节流互不干扰。static 保证跨 loop 调用保值，又不占全局命名空间。
  • 这不是教科书消抖。教科书消抖是"电平稳定 50 ms 才认"（要记录上次电平状态）；这里是"距离上次触发超过 50 ms 就再认一次"——按住不放，每 50 ms 都会触发一次。真正兜住它的是 loop 各分支里的 delay(300)：按键处理完强制停 300 ms，手指还没松开画面已经切完了，重复触发被延时窗口盖住。能自己指出"我的防抖是节流 + delay 兜底的组合"，比背教科书定义加分。
  • 低电平有效：INPUT_PULLUP 把脚拉到 5 V，按下接地变 LOW——所以判断 == LOW。
  • pin→index 的映射靠 if-else：四个按键写了四行。更工程的做法是按键表数组（pin、handler、优先级一行一个）——这页后面"如果重做"清单里的第一条。

优先级是怎么落地的

优先级按键动作对低优先级的清洗
1K1 总开关整机开/关，noTone，清屏badgeMode=false、currentNote=0——关机时一切归零
2K4 徽章模式位图 + 专属曲目K3 被屏蔽（切歌无效）；动画暂停
3K2 动画切换五角星 ⇄ 红旗清屏、重置 xOffset/waveOffset
4K3 音效切换小星星 ⇄ 东方红——（最底层，没人可清洗）

注意优先级不只是"先扫谁"——它是状态清洗的责任表。K1 为什么必须清 badgeMode？因为关机再开机时，徽章模式如果还挂着，开机第一帧就是位图而不是动画，用户会以为坏了。每个高优先级动作都要回答：我改变了哪些别人依赖的状态。

四个按键同时按下会怎样？

按 loop 的顺序依次响应：K1 翻转开关后 delay(300)——300 ms 里其他键的抖动窗口过去了；如果 K1 是关机，后面的 return 直接短路掉其余三个。顺序 + 延时 + 短路，三个机制叠出"总开关永远赢"。真要较真：K1 按下的同一帧 K2 也扫到了——但 K1 的 delay 让 K2 的效果发生在"下一次扫到"时，宏观上就是 K1 优先。

04

音乐：非阻塞播放到点取下一个音符——时间归 millis()，不归 delay

每首曲子就是两个一一对应的数组（频率表 + 时长表），播放器只有一个问题要答：上一个音符到时了吗？到点就 tone() 下一个，没到点立即返回去画动画。

FinalVersion…ino315–343 handleMusic
void handleMusic() {
  const uint16_t* currentNotes;
  const uint16_t* currentDurations;
  int noteCount;

  if (soundMode == 0) {
    currentNotes = defaultNotes;        // 小星星
    currentDurations = defaultDurations;
    noteCount = sizeof(defaultNotes) / sizeof(uint16_t);
  } else {
    currentNotes = dongfanghongNotes;   // 东方红
    currentDurations = dongfanghongDurations;
    noteCount = sizeof(dongfanghongNotes) / sizeof(uint16_t);
  }

  if (millis() - previousMusicTime >= noteDuration) { ①
    if (currentNote < noteCount) {
      // 从Flash读取数据
      uint16_t note = pgm_read_word(&currentNotes[currentNote]); ②
      uint16_t duration = pgm_read_word(&currentDurations[currentNote]);

      tone(BUZZER_PIN, note, duration);
      previousMusicTime = millis();
      currentNote++;
    } else {
      currentNote = 0;  // 循环播放
    }
  }
}
  • 比较的是"上一个音符的时长"noteDuration——它在上一次取音符时被…… 等等，仔细看：noteDuration 是全局变量，初值 500，而这个函数里从来没有更新过它。也就是说无论音符标多少毫秒，间隔恒为 500 ms——时长数组读出来只传给了 tone()（控制鸣响时长），音符间的间隔被钉死在 500 ms。这是读代码才发现的真实缺陷：读时长本来该赋给 noteDuration，漏了一行。听觉效果是"每个音等长"——恰好不算难听，所以一直没被发现。能讲出这个，说明你真的逐行读过自己的代码。
  • pgm_read_word 是本页主角（第 07 节展开）：数组在 Flash 里，普通下标 currentNotes[i] 在 AVR 上读不到，必须用专门的读指令。
  • tone() 是异步的：它配置 Timer2 产生方波后立即返回，鸣响 duration 毫秒后自动停——所以这行不阻塞。注意 tone 同一时刻只能发一个频率（一个定时器），单声道是硬件决定的。

tone() 的原理是什么？换 PWM 行不行？

tone 用 Timer2 的 CTC 模式翻转一个 GPIO 产生 50% 占空比方波，频率 = 定时器溢出率。PWM 不合适：PWM 控制的是占空比（能量），蜂鸣器要的是频率（音高）——同一个定时器，CTC 翻转才是正解。这也是"无源蜂鸣器 = 小喇叭"的含义：你给什么频率它响什么音。

05

五角星：算出来的图没有一张素材图——10 个顶点 + 三角形填充

五角星 = 5 个外顶点 + 5 个内顶点交替连线。顶点全部由三角函数算出，动画只是把圆心横坐标来回平移——图是算出来的，动是挪出来的。

FinalVersion…ino158–191 顶点与绘制
void calculateStarPoints(int centerX, int centerY, int outerRadius, int innerRadius, int points[20]) {
  float angleOffset = -PI / 2;   ①
  float step = TWO_PI / 5;
  for (int i = 0; i < 5; i++) {
    float outerAngle = angleOffset + step * i;
    points[2 * i] = centerX + outerRadius * cos(outerAngle);
    points[2 * i + 1] = centerY + outerRadius * sin(outerAngle);
    float innerAngle = outerAngle + step / 2;  ②
    points[2 * i + 10] = centerX + innerRadius * cos(innerAngle);
    points[2 * i + 11] = centerY + innerRadius * sin(innerAngle);
  }
}

void drawStar(int offsetX) {
  int centerX = u8g2.getDisplayWidth() / 2 + offsetX;
  int centerY = u8g2.getDisplayHeight() / 2 + 10;
  int outerRadius = 25;
  int innerRadius = outerRadius * 0.382;  ③
  int points[20];
  calculateStarPoints(centerX, centerY, outerRadius, innerRadius, points);

  u8g2.setDrawColor(1);
  for (int i = 0; i < 5; i++) {
    int next = (i + 2) % 5;   ④
    u8g2.drawLine(points[2 * i], points[2 * i + 1], points[2 * next + 10], points[2 * next + 11]);
  }
  for (int i = 0; i < 5; i++) {
    int next = (i + 2) % 5;
    u8g2.drawTriangle(
      points[2 * i], points[2 * i + 1],
      points[2 * next + 10], points[2 * next + 11],
      points[2 * next], points[2 * next + 1]);
  }
}
  • 起始角 −π/2：屏幕坐标 y 向下，−90° 指向屏幕上方——保证五角星"尖朝上"。坐标系翻转是图形代码的第一坑。
  • 内顶点在外顶点基础上转半步（step/2 = 36°）：10 个顶点均匀间隔 36° 排在两个半径的圆上——这就是五角星的全部几何。
  • 0.382 不是拍的：标准五角星的内半径 = 外半径 × sin(18°)/sin(54°) ≈ 0.382，也是黄金比例的 1/φ²。写 outerRadius * 0.382 一行就是数学；写成 0.5 就变成"胖海星"。
  • (i+2)%5 画出五角星路径：外顶点 0→2→4→1→3→0，每步跨两个尖——直线连完正好是五角星轮廓（不穿过中心）。再对每条边补一个三角形（内顶点当第三点）实现填充。
  • 动画 = centerX ± xOffset，offset 每帧 ±2、到 ±40 折返——来回平移。注意切动画时 xOffset 必须清零（第 01 节 anno ③），否则从红旗切回来时星星从旧位置起步。
0.382 的来历（面试可现场推）： 五角星内顶点落在两外顶点夹角的平分线上， 内半径 r 满足 r / R = sin(18°) / sin(54°) = 0.309 / 0.809 ≈ 0.382 （等价于 1/φ²，φ 为黄金比例 1.618）

为什么不用图片（drawXBM）画星星？

一张 50×50 位图 ≈ 313 B（Flash 或 RAM），改个大小要重新出图；三角函数版改一个数字就能缩放，且学习目的就是练习程序化绘图。位图留给真正画不出来的东西——徽章（第 07 节）。程序化 vs 素材的分界线：几何规则能描述的用算的，不规则的才用位图。

06

红旗：逐列正弦波每一列有自己的纵向偏移，整列搬——布料就是这么飘的

红旗飘动的全部秘密：对每一列 x，算一个 sin 偏移量，把这一列像素整体上下搬。时间每帧推进一点相位，波浪就流动起来。

FinalVersion…ino204–217 drawFlag
void drawFlag() {
  // 只清空红旗区域，保留其他UI元素
  u8g2.clearBuffer();  ①

  // 绘制带有波浪效果的红旗
  for (int x = 0; x < flagWidth; x++) {  ②
    float yOffset = sin((x + flagX) * 0.05 + waveOffset) * waveAmplitude;  ③
    for (int y = 0; y < flagHeight; y++) {
      u8g2.drawPixel(x + flagX, y + flagY + yOffset);  ④
    }
  }
  drawFlagpole();
  u8g2.sendBuffer();
}
  • 注释和代码打架：注释说"只清空红旗区域，保留其他 UI"，代码却 clearBuffer() 清了整屏——注释是旧的，代码是改过的（或反之）。真实项目里这种"注释漂移"到处都是，能指出来就是读得细。
  • 外层循环是列：70 列（flagWidth），每列算一次 sin。
  • 相位 = (x + flagX) × 0.05 + waveOffset：x 参与相位意味着相邻列错开一点——波浪在空间上展开；waveOffset 每帧 +0.2，意味着波形在时间上平移。空间频率 0.05 rad/像素 + 时间速度 0.2 rad/帧，两个参数定手感。幅度 waveAmplitude=3：旗面上下 ±3 像素。
  • 整列平移：38 行像素逐点画到 y + yOffset——一列刚体搬移，不拉伸。布料感来自"列与列之间的错位"，不是列内部的变形——最简单的一维波动。
  • 成本：70 × 38 = 2660 次 drawPixel/帧。U8g2 的 drawPixel 是缓冲内存写，一帧 30 ms 里画 2660 个点绰绰有余——但也是这个项目帧率的上限所在（换 160×120 的旗就吃力了）。

为什么用 sin((x+flagX)·0.05) 而不是 sin(x·0.05)？

加 flagX（旗面左上角 x=30）让波形相位跟随旗面位置——挪旗面时波浪图案不变。是"世界坐标 vs 局部坐标"的小版本：先换到世界系再算相位。不加也能跑，挪旗时条纹会"穿过"旗面。

PROGMEM 与双地址空间AVR 的"放进去"为什么不是加个修饰符就完事

AVR 是哈佛结构：程序 Flash 和数据 SRAM 是两套独立的存储、两条独立的总线、两套独立的寻址指令。一个指针只能指向其中一套的地址空间——这就是 PROGMEM 故事的全部背景。

它在做什么

把只读的大数据（位图 1024 B、乐谱各 40–120 B）从 SRAM 搬进 32 KB 的 Flash——和程序代码住在一起。

它怎么做到的

数组声明加 PROGMEM（展开后是 __attribute__((section(".progmem.data")))），链接器把它放进 Flash 的数据段；读取时用 pgm_read_byte / pgm_read_word——它们展开成 LPM 指令（Load Program Memory），这是 AVR 唯一能按字节读 Flash 的指令。

为什么必须这样

不加 PROGMEM 的 const 数组照样占 SRAM——AVR 的 C 启动代码会把初始化数据从 Flash 复制到 SRAM（.data 段搬运），const 在这个平台上不省 RAM。而 Flash 里的地址和 SRAM 地址不是一套编码：直接拿指针下标读，读到的是 SRAM 里同地址的别的东西——花屏、乱音、随机死机的来源。

FinalVersion…ino220–221 位图声明（数据共 64 行×16 字节）
// ================= 党徽位图数据 =================
const unsigned char party_logo[] PROGMEM = {
  0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x0c, 0x00, ...
  // 共 64 行 × 16 字节 = 1024 字节（128×64 ÷ 8）
};
FinalVersion…ino307–312 位图显示
void drawBadge() {
  u8g2.clearBuffer();
  // 关键修改：使用支持PROGMEM的显示方法
  u8g2.drawXBMP(0, 0, 128, 64, party_logo);  ①

}
  • drawXBMP 是 PROGMEM 版的位图绘制：普通 drawXBM 接受 RAM 指针，drawXBMP 内部用 pgm_read_byte 从 Flash 逐字节取。注释里那句"关键修改"就是当年崩溃现场的化石——从 drawXBM 换成 drawXBMP 是修复的一环。
  • 位图格式 XBM：每位一个像素、MSB 在前、每行 16 字节对齐。1024 字节正好整屏。
  • 乐谱读取用的是 pgm_read_word（uint16 两个字节）：pgm_read_word(&currentNotes[currentNote])——注意取地址再交给宏。普通下标 currentNotes[i] 编译能过、运行读错——这是最阴的坑：不报错，只出鬼。

为什么 ARM/ESP32 上不用这么麻烦？

Cortex-M 和 ESP32 是统一编址（冯·诺依曼式的地址空间）：Flash、RAM、外设挂在同一张地址表上，const 数据留在 Flash 里用普通指针就能读——编译器顺手就把 const 放 .rodata 段了。所以 PROGMEM 是 AVR 特有的痛，但"只读数据别占 RAM"的意识是通用的：ESP32 项目里的字符串常量照样该进 Flash。

2 KB 危机全过程现象 → 定位 → 修复 → 复盘——大一的第一次内存事故

这是整个项目的核心叙事：屏幕花屏、随机复位——不是代码错，是数据没地方住。以下按"事故报告"的顺序讲，每一步都可以直接搬进面试。

① 现象

加上全屏位图后：屏幕花屏（显示乱块）、机器不定时自己重启、偶尔按键失灵。三个症状一起出现且随机——典型的"内存被踩"而非逻辑 bug。

② 定位

花的是屏、复位的是机——嫌疑落在缓冲和数据区。逐项排除：注释掉位图显示就正常，恢复就坏——锁定 party_logo。再看数据手册：2 KB 总量，U8g2 全屏缓冲已占一半。

③ 修复（三件套）

位图加 PROGMEM + 显示改 drawXBMP；两首乐谱加 PROGMEM + 读取改 pgm_read_word。SRAM 里只留 U8g2 缓冲和活变量——腾出约 1.1 KB，症状全部消失。

④ 复盘（读代码时新发现）

第三首乐谱 customNotes（120 B）漏加了 PROGMEM，至今躺在 RAM 里——修复后余量足够所以没炸，但"全部移入 Flash"的说法对它不成立。连同 noteDuration 恒为 500 ms 的漏更新，这两处是后来 code review 才看见的。

事故前的内存账（ATmega328P：2048 B SRAM）： U8g2 全屏显示缓冲 1024 B party_logo 位图 1024 B ← 罪魁（当时还在 RAM） 小星星+东方红乐谱 ~104 B customNotes 乐谱 120 B ← 漏网之鱼 全局变量/栈/串口缓冲 ~200 B ───────────────────── 合计 ≈ 2472 B ＞ 2048 B → 栈顶往下长，撞进 .bss/.data → 全局变量被栈覆盖 = 花屏；返回地址被踩 = 随机复位 修复后（位图+两首乐谱进 Flash）：≈ 1348 B，余量 700 B
为什么症状是"随机"的栈从 SRAM 顶部往下长，全局数据从底部往上排——两者相撞的位置取决于当时的调用深度。画位图那几层调用深，撞上了就花屏；中断或函数返回时撞上返回地址，就复位。撞不撞、撞坏什么，每次都不一样——"随机性本身就是栈溢出的指纹"，这句话面试可以直接用。

当时没有的工具，现在要知道

  • avr-gcc -Wl,--gc-sections -Wl,--print-memory-usage：链接时打印 Flash/RAM 实际用量——编译期就能看到离爆还有多远。
  • IDE 里 编译输出底部的 "Global variables use XXX bytes"——就是这张账单，当年没看懂它。
  • 运行时监控：freeRam()（读 __brkval 和栈指针的差）可以画在屏幕上实时看。

如果 PROGMEM 都上了还是不够呢？

按代价从小到大：①U8g2 换 F（全缓冲）为 U8x8 或分页模式——1024 B 缓冲直接省掉，代价是没字体抗锯齿；②位图改压缩（RLE）或分屏加载；③换芯片——328P 的 2 KB 是硬顶。真实世界大多选 ①或 ③。

追问链：从 PROGMEM 挖到链接与启动

  1. L1"PROGMEM 是宏还是关键字？"——宏：展开成 __attribute__((section(".progmem.data")))，把数据放进自定义段。
  2. L2"链接器和启动代码在这中间干了什么？"——链接器按段分配 Flash 地址；不带 PROGMEM 的初始化数据（含 const）会被启动代码 crt 从 .data 段复制进 SRAM（这就是 const 不省 RAM 的机制）；带 PROGMEM 的段只留在 Flash。
  3. L3"那 .bss 和栈呢？"——.bss 不占 Flash 只占 SRAM（启动时清零）；栈从 SRAM 顶往下、.data/.bss 往上，中间的空隙就是可用余量——freeRam() 就是量这个空隙。我那次花屏就是空隙被挤没了，栈写穿进了全局区。能画出这张内存地图，这条链就满分。

  • ■ AVR 上 const 不省 RAM——初始化数据照样被复制进 SRAM；只有 PROGMEM 才真留在 Flash。
  • ■ Flash 里的数组必须用 pgm_read_* 读——普通下标编译能过、运行读错，"不报错只出鬼"。
  • ■ 花屏 + 随机复位 = 先查内存：栈撞全局区的指纹就是随机性。看编译输出底部的 RAM 用量。
  • ■ "50 ms 节流"不是消抖——按住会重复触发；真消抖要记电平稳定。节流 + delay(300) 组合才等效"按一下动一下"。
  • ■ 模式切换必清状态：currentNote、xOffset、waveOffset……漏清哪个，哪个就串台。
  • ■ 优先级不只是顺序——短路（return）和屏蔽（条件带 !badgeMode）才是"总开关永远赢"的保证。

自测 8 题两道必须动笔算

答案默认折叠。先写下来再展开。

【算】128×64 单色位图多少字节？若是 RGB565 彩屏同分辨率又是多少？

单色：128 × 64 ÷ 8 = 1024 B（每像素 1 bit） RGB565：128 × 64 × 2 = 16384 B = 16 KB ——彩屏全屏位图在 2 KB 的板子上根本不可能常驻（ESP32 项目降 8 bit 的远因）

【算】事故前后的内存账：U8g2 缓冲 1024 B + 位图 1024 B + 三首乐谱 + 活变量 ≈ 多少？修复后呢？

修复前 ≈ 1024+1024+104+120+200 ≈ 2472 B ＞ 2048 B（栈撞全局区） 修复后（位图 + 两首乐谱进 Flash，第三首漏掉仍在 RAM）≈ 1348 B，余量约 700 B ——那 120 B 的漏网之鱼就是"侥幸能用"的余量来源

按住 K2 不松手，会发生什么？两道防线分别挡住了什么？

50 ms 节流窗挡机械抖动（5–10 ms 的通断弹跳）；但按住不放每 50 ms 仍会触发——真正挡长按的是处理完的 delay(300)：300 ms 内 loop 不转，手指没松也只切一次。若去掉 delay(300)，按住 1 秒会连切约 19 次动画。

为什么修复内存时必须同时改三处（声明加 PROGMEM、显示换 drawXBMP、读取换 pgm_read_word）？只改一处会怎样？

①只加 PROGMEM 不换读法：数据进了 Flash，但普通下标仍走数据空间——读到 SRAM 同地址的别的东西，花屏变"另一种花屏"；②只换 drawXBMP 不加 PROGMEM：drawXBMP 用 LPM 读一段实际在 SRAM 的数据——同样读错（反向的错）；③三处必须成套换——存储位置、读指令、写法是绑定的三件套，少一件都是"不报错只出鬼"。

tone() 和 millis() 各用哪个定时器？为什么音乐和动画能同时跑？

tone() 用 Timer2 的 CTC 翻转产生方波（异步，启动即返回）；millis() 用 Timer0 的溢出中断计时。两者硬件独立、互不占用。音乐每圈 loop 只做一次"到点了吗"的比较，动画每 30 ms 一帧——两条时间线在同一个 loop 里交错推进，谁都不独占 CPU。

noteDuration 这个全局变量现在实际控制什么？本来的设计意图可能是什么？

实际控制：音符的取下一个的间隔——恒为初值 500 ms（handleMusic 从不更新它）。设计意图显然是"当前音符的时长"（读出 duration 后应赋给 noteDuration），漏了一行赋值。后果：快歌慢歌都被拉成等间隔的"节拍器"节奏——时长数组只剩下控制 tone 鸣响时长的作用。修复：取音符时加 noteDuration = duration;。

五角星内半径 0.382×R 怎么来的？写成 0.5 会看到什么？

标准五角星内/外半径比 = sin(18°)/sin(54°) = 0.309/0.809 ≈ 0.382 = 1/φ²。写成 0.5 内顶点外扩，五个尖被压短——"胖海星"。0.382 是几何定值不是美学参数；美学只决定你要不要标准五角星。

如果面试官问"这项目如果换 STM32 你会保留什么、扔掉什么？"怎么答？

保留：非阻塞骨架（millis 轮询）、按键优先级与清洗责任表、程序化绘图。扔掉：PROGMEM/pgm_read 全套（统一编址下 const 自动进 Flash）——但"只读数据不占 RAM"的意识保留，只是实现从"手工搬"变成"编译器代劳"。再进一步：STM32 有 DMA 和定时器中断，音乐的"到点检查"可以升级成定时器中断驱动——但轮询版本依然是能跑的最简实现。
