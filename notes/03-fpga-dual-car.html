00

开场：怎么把这个项目讲出去面试前 30 秒定生死：先给脚本，再谈细节

30 秒 · 电梯版

数电课设团队项目，两辆车用同一套 VHDL 逻辑做协同：领车按键启动时发一串红外脉冲，跟车收到立刻起步；之后跟车一边循迹、一边用超声波测与前车的距离，分四档调速跟随。圈数计数用"全黑持续 15 ms 确认 + 1 s 冷却 + 圈内锁存"三重条件，四圈不串圈。我负责决策模块 tracking_logic 和顶层集成。整个系统在 50 MHz 单时钟域内闭环，没有 CPU、没有软件、没有中断——所有决策都是时钟沿上算出来的。

角色边界：决策模块 tracking_logic（约 240 行）、顶层 smart_car 的例化与连线、蜂鸣器逻辑、总体架构划分是我写的；扫描、超声、红外、PWM 四个外设模块由组员按接口定义实现（接口划分推断为我提出，按实际讲）。
2 分钟 · STAR 版

S｜两辆车既要同步起步（人工喊口令不齐），又要在跑动中保持距离——不撞前车、也不被甩掉。T｜各自沿黑线跑满四圈，圈数不能多计；跟随区间 60–400 mm 稳定调速；跑完停车鸣笛一次。A｜四件事：①把系统拆成扫描、测距、红外、决策、PWM 五个模块，顶层只做例化连线，每个模块可单独仿真替换；②圈数三重条件防串圈——15 ms 持续确认、1 s 冷却、圈内锁存；③循迹用 8 路状态直接查表，全白时"记忆上次转向方向"扛过丢线；④跟随按距离四档（>400 回正常 / 200–400 加速 / 100–200 正常 / <100 减速 / <60 停车），因为超声读数噪声大，分档比连续 PID 稳。R｜两车协同启动、四圈计数不串圈、稳定跟随、停车蜂鸣一次不重复。遗留：路口锁定时间是固定值，车速变了要重调；循迹只有分档差速，没有连续偏差控制。

讲法提醒这个项目的面试价值在于"硬件思维和软件思维的差别"：单片机是逐条执行，FPGA 是同时存在。所有"等一会儿"都是计数器不是延时函数，所有"分支"都是并行硬件。先立住这个反差，再讲模块——面试官会自己往下问。
01

没有 CPU 的世界怎么决策建立整体印象：同时存在的五块逻辑 + 一条时钟节拍

单片机项目读代码是读"执行顺序"；这个项目读代码是读"谁连着谁"——五个模块在同一个 50 MHz 时钟下同时、永远、反复地算各自的输出，决策模块每个时钟沿都重新给一次左右轮速度。

从结构看

顶层 smart_car.vhd 只做两件事：声明六个 component、把它们端口连起来。功能全部在子模块里，顶层 0 行业务逻辑（蜂鸣器除外，它写在顶层）。

从时间看

整个系统只有一个节拍：50 MHz 时钟沿。没有调度、没有优先级——"慢"不是靠等待，是靠计数器数够时钟数（15 ms = 750000 个周期）。

从角色看

tracking_logic 是唯一"做决定"的模块：输入 8 路线状态 + 距离 + 启动信号，输出左右轮速度 0–100。其余四个模块都只管一件事：把物理世界的量变成数字。

为什么这套系统适合放 FPGA，而不是再拿一个单片机做？

三个理由：①需要精确的并行时间窗——15 ms 确认、1 s 冷却、38 kHz 载波同时跑，单片机要靠定时器拼；②双车是课设题目要求展示数字系统设计能力；③模块化在 FPGA 里是"物理隔离"——改一个模块不影响其他模块的时序，比 C 的函数隔离硬得多。

02

顶层：例化即集成smart_car.vhd · 256 行 · 唯一的业务逻辑是蜂鸣器

顶层文件是一张电路图，不是一段程序：声明六个元件（component），用端口映射（port map）把线连上。读懂顶层的标志是——只看端口名就能画出系统框图。

一、先看接口：这个系统对外是什么

entity 的 port 列表就是开发板的接线表。读它的时候问自己一个问题：每个信号是"外设固定脚"还是"自己选的"？

  • 复位是低有效（sys_rst_n，n = negative）。整个项目所有进程的复位分支都写 if sys_rst_n = '0'——这是 FPGA 的惯例，开发板按键按下接地。

  • 电机是 PWM + 两根方向线的标准 H 桥接法。注意：顶层把方向线写死为正转（后面会看到），所以这个系统没有倒车——丢线后不能倒回去找。
  • 圈数指示只有 2 位 LED，要显示 0–4 五个状态——2 位只能编码 4 个。这个"装不下"埋下了后面第 10 节要讲的真 bug。

顶层为什么不把逻辑全写在一个文件里？

三个理由，按分量排：①可单独仿真——每个模块独立写 testbench，不依赖整车；②改动隔离——改循迹只重综合 tracking_logic，其他模块的时序不受牵连；③端口即文档——五个 port map 就是团队分工的合同，谁负责什么一目了然。

component 声明和直接写 entity 有什么区别？

component 声明是"我知道有个元件长这样"的前向引用，配合 port map 用；直接例化（entity work.xxx）可以省掉声明，但把顶层和具体架构绑死。这个项目用传统 component 写法，和教科书一致——讲的时候点一句你知道两种都行。

灰度扫描 sensor_scanner50 行 · 3 根地址线轮流"点名"，每路等 100 μs

8 路灰度共用 1 根输出线：地址线给编号，OUT 吐电平。这个模块就是一个永不停止的循环点名器——0 号、1 号、……7 号、再回 0 号，每换一个人等 100 μs 让他开口，把答案记进 8 位寄存器。

一、全貌：两个计数器撑起的循环

sensor_scanner.vhd18–49 全部逻辑
architecture Behavioral of sensor_scanner is
    signal channel_idx : integer range 0 to 7 := 0; ①
    signal delay_cnt   : integer range 0 to STABLE_TIME := 0; ②
    signal temp_data   : STD_LOGIC_VECTOR (7 downto 0) := (others => '0');
begin
    process(clk, rst_n)
    begin
        if rst_n = '0' then
            channel_idx <= 0;
            delay_cnt <= 0;
            ad_pins <= "000";
            data_ready <= (others => '0');
        elsif rising_edge(clk) then
            -- 输出地址
            ad_pins <= std_logic_vector(to_unsigned(channel_idx, 3)); ③
            
            if delay_cnt < STABLE_TIME then ④
                delay_cnt <= delay_cnt + 1;
            else
                -- 采样: 1=黑, 0=白 (根据你刚才的测试结果) ⑤
                temp_data(channel_idx) <= sensor_out;
                
                delay_cnt <= 0;
                if channel_idx = 7 then
                    channel_idx <= 0;
                    data_ready <= temp_data; -- 更新一帧数据 ⑥
                else
                    channel_idx <= channel_idx + 1;
                end if;
            end if;
        end if;
    end process;
end Behavioral;
  • channel_idx 是"点名到几号"，range 0 to 7——数值范围写进类型里，综合器会自动截掉高位，写错范围综合阶段就暴露。
  • delay_cnt 是"这轮等了多久"，上限就是泛型 STABLE_TIME := 5000。数到头才允许采样——这是这个模块唯一的"耐心"。
  • 地址每拍都在输出（不只是切换那一拍）。赋值语句放在 if 外面，意味着 ad_pins 永远忠实反映 channel_idx——多花不了任何资源，但省去了"什么时候更新地址"的判断。
  • STABLE_TIME = 5000 个时钟 = 100 μs。切换地址后模块内部的模拟开关需要建立时间，电平没稳就读，读到的是上一路的残留。
  • 注释里的"根据你刚才的测试结果"是调试时留下的原话——1=黑、0=白的极性是实测定的，不是手册定的。讲项目时这种痕迹反而证明你上过手。
  • temp_data 攒够 8 位才搬进 data_ready：读第 0–6 路时，输出侧还在用上一整帧旧数据；只有扫完第 7 路，新的一帧才"原子地"整体可见——决策模块永远拿到完整一致的一帧，绝不会看到半新半旧。

三、和 PIC 小车同一个传感器，两种做法

PIC 版（微机课设）FPGA 版（本项目）
切地址后等稳定CPU 空转 80 个循环（≈80 μs，volatile 防优化）计数器数 5000 拍（100 μs），硬件自动
抗干扰每路采 3 次、≥2 次为高才认（表决）单次采样，没有表决——省了逻辑，靠决策端查表容错
数据一致性读一次用一次，函数返回时才有效永远有最新一帧挂在总线上，决策随取随用
占用资源主循环时间（每读一遍 ≈1 ms）一个独立进程 + 两个小计数器，不占别人时间
面试话术被问"两个项目都用 3-8 选通，学到什么"：同一块传感器板，在 CPU 上是"函数调用"，在 FPGA 上是"独立进程"——接口一样，时间模型完全不同。FPGA 版不需要表决反而能工作，是因为决策端查表天然容忍单路误判。

STABLE_TIME 为什么是 5000？大了小了分别会怎样？

5000 ÷ 50 MHz = 100 μs，覆盖选通开关的建立时间。小了：读到上一路残留，表现为"偶发串道"——本该全白的某一路闪黑。大了：一帧变长、帧率下降，过线检测的响应变慢。100 μs 是实测能稳的最小值量级（泛型参数化方便现场重调）。

data_ready 这个名字合适吗？

不合适——它输出的是8 位数据本身，不是"准备好了"的单 bit 标志。命名会误导读代码的人。讲的时候可以主动指出：更好的做法是拆成 data 和 valid 两根线，或者改名 sensor_frame。

  • echo_cnt 上限 5000000 = 100 ms：对应最大量程。声波 100 ms 走 340×0.1 = 34 m，往返 17 m——远超 HC-SR04 标称 4 m 量程，这个上限够用。但如果 echo 卡在高电平超过 100 ms，计数器会越界——第 10 节详谈。
  • 294 是整个模块的灵魂，下面现场推导。
声速 ≈ 340 m/s，1 mm 往返飞行时间： t = 2 × 1 mm ÷ 340 m/s = 5.88 μs 折成 50 MHz 时钟周期： n = 5.88 μs × 50 周期/μs = 294 周期/mm 验算：echo 高电平 5880 个周期 ÷ 294 = 20 mm ✓ （echo_cnt 上限 5000000 ÷ 294 ≈ 17000 mm ≫ 量程 5000 mm ✓）

二、主进程：造波、计时、换算

  • trig 脉冲宽度由同一个计数器兼职产生：trig_cnt < 1000（=20 μs）期间 trig 为高。一个计数器既定周期又定脉宽——省一个计数器的代价是两个参数耦合，改周期必看脉宽。
  • echo 进时钟域前打了两拍（echo_sync(0) → (1)）。echo 是异步外部信号，直接用可能在时钟沿附近违反建立/保持时间，触发器输出进入亚稳态——既非 0 也非 1 的中间电平，往后传染。两级同步器是标准解法：第一拍允许"抖"，第二拍输出的已经是稳定值。这是全项目唯一真正用上的同步器——红外的接收信号没这么处理（第 05、10 节）。
  • 秒表逻辑：echo_sync(1) 为高就 +1。注意计的是同步后的信号，所以 echo 实际边沿被延迟了两拍（40 ns）——对毫米级精度无感。
  • 除法在 else 分支里，意味着"echo 不为高的每一拍"都在算 echo_cnt ÷ 294。综合器必须生成一个真实的除法器，50 MHz 单拍完成 23 位÷9 位，这是本模块时序最紧的路径（推断：综合报告里它大概率是关键路径）。更稳妥的写法是只在 echo 下降沿那一拍算一次，或用乘法+移位代替。

三、一次测量的完整时序

两个隐蔽行为①距离 0 有双重含义：echo 从没来过（开机、丢波）时 distance_mm 也是 0——决策模块把 distance_mm = 0 和 > 400 合并成"跟丢"，歪打正着，但这是约定俗成而不是设计出来的哨兵值。②stop_flag 与决策模块的停车判断重复：这里判了 <60，tracking_logic 里又判了一次——stop_req 线根本没用（第 10 节）。

为什么要两级打拍？一级不行吗？

一级同步器的问题是：那一拍输出可能正处亚稳态，下一级电路立刻用它就会出错。第二拍的作用是给亚稳态一个完整的时钟周期去稳定。两级不能根绝亚稳态（概率按指数下降但不为零），但对 50 MHz、MTBF 要求普通的系统足够；高可靠性场景上三级并加 FIFO 做跨域握手。

为什么 20 ms 测一次，不是越快越好？

三个限制：①HC-SR04 手册建议测量周期 ≥60 ms 防回波串扰（这里取 20 ms 偏激进，靠"距离变化平滑"扛住了，推断）；②每帧循迹 0.8 ms，测距密度远高于循迹就够了；③测得太密，前车反射的多次回波会互相污染。四档跟随对距离更新率的要求本来就不高。

四、空中的波形长什么样

为什么红外一定要载波环境光（阳光、灯光）里有大量红外成分，直流点亮发射管根本区分不开。把信号调制到 38 kHz，接收头内部带通滤波器只认这个频率的"闪烁"——用频域换信噪比。这和收音机要载波是同一个道理，面试被问到"为什么要 38 kHz"时往这个方向答。

这个握手可靠吗？跟车漏收了会怎样？

单向、无确认、无重发——严格说不可靠。漏收的后果是跟车永远停在 state_lap=0。工程化做法：领车每隔 500 ms 重发直到收到跟车的回执（双向握手），或至少重发三次。课设里省掉，是因为两车距离近、一次成功率实测够高。说清"知道它不可靠、为什么当时可以接受"，比假装它可靠强。

rx_detect 为什么做成单拍脉冲而不是电平？

决策端只需要"事件"不需要"状态"。如果做成持续电平，决策模块还得自己记"处理过没有"；单拍脉冲让每次接收天然是一次性事件。代价是决策端那一拍必须醒着——好在决策模块每个时钟沿都在跑，不存在错过。

  • 条件三：圈内锁存 lap_count_flag——冷却期结束到下一次过线之间，只允许计一次。它挡住的是"冷却刚结束、车还没完全离开线"的边角情况：冷却清零了 black_duration_cnt，但 lap_count_flag 还记得这一圈计过了。
  • state_lap=3 时跳到 4——第四段不叫"第四圈"而叫"完成态"，进入后速度归零、蜂鸣器响。注意 3→4 用的条件和 1→2、2→3 完全一样，没有特殊化——四圈的一致性就是靠不特殊化保证的。
三个时间常量的来历： 15 ms 确认 = 跨过线宽的时间下限（车速 ≈ 0.3 m/s ÷ 线宽 1.8 cm ≈ 6 ms，取 2.5 倍余量） 1 s 冷却 = 一圈内两次压线的最小间隔（圈时 ≈ 20 s，取 1/20 也留足） 5000000 拍 Y 锁定 = 100 ms（车速 × 车长量级，推断为实测调出）

去掉任何一个条件会怎样？

去掉 15 ms：毛刺误计。去掉 1 s 冷却：车头车尾分两次压线，一条线计两次。去掉锁存：冷却刚结束、车尾还在线上，同一条线再来一次。三个条件分别对付毛刺、车长、边界三种物理来源的误判——这是"对着现象设计"而不是"拍脑袋加滤波"。

为什么 state_lap 用 integer 不用自定义枚举？

枚举（type lap_t is (IDLE, LAP1, ...)）可读性更好，综合器自动编码。这里用 integer range 0 to 4，好处是 state_lap+1 这种推进可以直接写算术、范围约束自带保护（越界即仿真报错）。两种都对，讲的时候说"知道枚举更规范，这里图算术方便"。

全白丢线时为什么"记忆方向"而不是停车？

全白最常见的原因是车冲过了线（动态丢线），不是真离轨。停车就永远停在那了；按 last_act 继续转，车头会画弧扫回线上。代价：如果是真脱轨，车会原地画圈回不来——这个系统没有倒车，找回策略做不了闭环，是已声明的局限。

查表和"算偏差量"（重心法）怎么选？

8 路开关量没有天然的偏差量——要做重心法得先给每路加权求平均，再做 PID。查表直接把 21 个有效组合映射成动作，省资源、好调、行为完全可预测（每种输入都能在表里查到答案）。代价是没有中间档——"偏 5°"和"偏 30°"是同一个动作。传感器升级到模拟量（如 8 路 ADC）才值得上连续控制。

motor_pwm 与蜂鸣器36 行 PWM + 顶层里的两段蜂鸣器逻辑

决策输出的是 0–100 的速度数字，电机认的是占空比波形——motor_pwm 就是这中间的翻译官。它被例化了两次（左右轮各一），这是"模块复用"最直白的样子。

motor_pwm.vhd13–36 全部逻辑
architecture Behavioral of motor_pwm is
    constant PERIOD : integer := 50000; -- 1kHz 频率 ①
    signal cnt : integer range 0 to PERIOD := 0;
begin
    process(clk, rst_n)
    begin
        if rst_n = '0' then
            cnt <= 0;
            pwm_out <= '0';
        elsif rising_edge(clk) then
            if cnt < PERIOD - 1 then
                cnt <= cnt + 1;
            else
                cnt <= 0;
            end if;

            if cnt < (duty * 500) then ②
                pwm_out <= '1';
            else
                pwm_out <= '0';
            end if;
        end if;
    end process;
end Behavioral;
  • 50000 拍 = 1 kHz PWM 周期：50 MHz ÷ 50000。1 kHz 对有刷直流电机足够——电枢的机械惯性行为就是低通滤波器，1 kHz 的纹波到转轴上已经磨平。
  • duty × 500 = duty% × 50000：把 0–100 的百分数换算成 0–50000 的拍数。duty=55 → 前 27500 拍高电平。乘法每个时钟沿都算——duty 是外部输入，综合器会生成一个小乘法器（8 位 × 常数 500，实为移位相加：500 = 256+128+64+32+16+4），代价可接受。
  • 占空比每拍重算：cnt 在周期中段时 duty 变了，输出的高电平长度当拍就跟着变——不需要等下个周期对齐。简单，代价是理论上的毛刺（占空比中间跳变），对电机无感。

以下五个问题全部来自源码原文，不是假设。它们的共同点是：实测都没炸，但每一个都有一条"如果条件再苛刻一点就炸"的路。面试官问"这个项目有什么可以改进的"时，按这个顺序讲。

#1 w_lap_info 的 "11" 歧义 —— 蜂鸣器会提前响

tracking_logic.vhd59 debug_lap 编码
    debug_lap <= std_logic_vector(to_unsigned(state_lap, 2)) when state_lap < 4 else "11";

推演：state_lap=3 时 to_unsigned(3,2) = "11"；state_lap=4 时 else 分支也是 "11"。第三圈进行中和跑完，输出完全一样。蜂鸣器条件是 w_lap_info="11" and w_speed_l=0——第三圈中途只要车被超声逼停一次（<60 mm），蜂鸣器就提前响，且 buzzer_has_ring 锁定后，真跑完时反而不响。

为什么实测没炸：跟车与前车距离管理得住，第三圈没触发过 <60 mm 停车。正确写法：debug_lap 用 3 位（0–4 需要 3 根线），或让 "11" 只属于状态 4——比如 state_lap=3 时输出 "10"（2 位只能表示 0–3，干脆把"完成"编码成全 1 且让状态 3 不输出全 1：用 00/01/10/11 分别对应 1/2/3/完成，等待态也归入 00）。

#2 stop_req 接而未用 —— 接了设备的空插座

事实：hc_sr04 输出 stop_flag（<60 mm 时拉高），顶层把它连到 tracking_logic 的 stop_req 端口——但 tracking_logic 的进程体里一次都没引用 stop_req。停车实际是决策模块拿 distance_mm < 60 自己判的。

影响：功能上无（两处判的是同一个数），但它是一次接口演化的化石——推测早期设计是"超声模块直接给停车信号"，后来跟随逻辑改成四档，停车并进了 follow_ratio=0，这根线就成了遗迹。讲法：端口留下没问题，但要能说出"这根线现在是死的，为什么当时留着"——接口留余量 vs 死代码，一线之隔。

#3 ir_sync 的两级同步器声明了没用 —— 亚稳态敞口

ir_sync.vhd41–43 vs 123
    signal rx_sync_0  : std_logic := '1';
    signal rx_sync_1  : std_logic := '1'; -- 打两拍消除亚稳态
    ...
                if ir_rx_pin = '0' then   -- ← 实际直接用了原始引脚

推演：ir_rx_pin 是异步外部信号（红外接收头的输出与 50 MHz 时钟无相位关系）。直接在时钟沿采样，违反建立/保持窗口时触发器输出亚稳态，这个中间电平传进 rx_cnt 比较逻辑，理论上可能误判。超声模块的 echo 做了两级同步（echo_sync），红外这里没做——同一个项目、同类异步输入、两种待遇。

为什么实测没炸：亚稳态概率本来就低（每拍约 10⁻⁶ 量级以下），且启动信号只收一次、持续 9 ms——暴露窗口极小。正确写法：把两处 ir_rx_pin 换成 rx_sync_1，三行代码的事。这是五个问题里修复成本最低、面试价值最高的一个。

#4 w_speed_r 的 range 是 0 to 5000 —— 复制粘贴的化石

事实：顶层里 w_speed_l 是 range 0 to 100，w_speed_r 是 range 0 to 5000——右轮明显是从 w_distance_mm（0 to 5000）那行复制过来改漏的。实际速度值 ≤100，所以侥幸不越界。

什么时候会炸：仿真里任何一个分支给右轮超过 5000，仿真器立刻报整数越界停下；综合后 FPGA 上则是高位被截（无保护）。它同时也是个 lint 提醒：VHDL 的 range 约束是好东西，但约束错了比没有更危险——它给了你"这变量查过了"的错觉。

#5 echo 卡高 100 ms 会溢出；echo 丢失则距离冻结

推演 A（溢出）：echo_cnt 的 range 是 0 to 5000000（=100 ms）。如果 echo 引脚被干扰或器件故障卡在高电平，计数器数到上限后越界——仿真直接报错；上板则是行为未定义。正确写法：加 if echo_cnt < 5000000 then echo_cnt <= echo_cnt+1 的饱和保护，并把"数满"解释为无效测量。

推演 B（冻结）：distance_mm 只在 echo 拉低的那一拍更新——某次测量 echo 丢失时，输出保持上一个旧值。跟车会按 20 ms 前的距离继续跑。决策端 distance_mm=0 的哨兵只覆盖"从未测到"，覆盖不了"测到一半丢了"。正确写法：加超时标志，超时强制 distance 归零（正好落进"跟丢"分支）。

这两个都属于"实测场地干净所以没炸"的典型——把它们讲清楚，就是在展示对失效模式的想象力，这恰恰是硬件岗位最看重的。

怎么在面试里用不要说"我们的代码有问题"——说"后来重读代码时我发现了五个可以在下一次迭代修掉的问题"，然后按"现象推演 → 为什么当时没炸 → 怎么修"三段讲一两个。主动权在你手里：这些是你自己 code review 出来的，不是被人挑出来的。

追问链：FPGA 岗最常挖的三条线

链 A：从同步器挖到亚稳态本质

  1. L1"你项目里哪里用了同步器？"——echo 两级打拍（顺手指出红外 rx_sync 声明了没用，知道是坑）。
  2. L2"两级就够了吗？失效概率是多少量级？"——不能根绝，指数下降：单级亚稳概率 ~10⁻⁶/拍量级（取决于器件和频率），两级再乘一个衰减因子，MTBF 从"天"拉到"千年"以上。
  3. L3"那多比特数据怎么跨域？两拍不就撕裂了？"——握手或异步 FIFO：发送侧把数据打进双口 RAM/FIFO，用一个经过同步的"写完成"脉冲通知对侧；格雷码指针防读写在同一拍翻转。能主动说到格雷码，这条线就满分。

链 B：从除法器挖到时序收敛

  1. L1"你代码里有除法，FPGA 里除法怎么实现？"——综合器生成组合除法器（级联的减法-移位结构），面积大、路径长；本项目 ÷294 出现在每拍的 else 分支里。
  2. L2"50 MHz 能收敛吗？怎么确认？"——跑 STA 看这条路径的 slack（推断它是关键路径）。负 slack 的修法：只在 echo 下降沿那一拍算一次（把常驻除法变偶发）、乘倒数（294⁻¹ 定点化）+ 移位、或加一级流水。
  3. L3"为什么流水线能救时序？代价呢？"——切组合逻辑为 N 段，每段一个周期的建立时间预算，代价是延迟 +N 拍和 N 个寄存器。测距路径多 1–2 拍延迟（40 ns）对毫米级精度零影响。

链 C：从模块划分挖到团队协作

  1. L1"五个人（按实际人数讲）怎么分工的？"——先定五个模块的端口，再分头写；我负责 tracking_logic 和顶层集成，所以接口划分实际上是我牵头定的（按实际调整）。
  2. L2"接口怎么定的？改过吗？"——按数据流方向定：传感器类模块只输出、决策只消费；中途加红外时给 tracking_logic 加了两个端口（代码注释里还能看到【新增】的痕迹）。改接口的成本就是所有 port map 重对一遍，所以第一版宁可多留（也留下了 stop_req 这种没用上的）。
  3. L3"如果模块间时序对不上怎么办？"——加 valid/ready 握手或 FIFO，让消费方明确知道"这帧数据好了没有"。本项目靠"永远有最新帧"的推模型（scanner 持续输出）省掉了握手——因为灰度数据是状态不是事件，旧的也能用。

12 条

  • ■ signal 进程末才更新、variable 立即更新。想在同一拍里"算完就用"必须用 variable——tracking_logic 的速度流水线就靠它。
  • ■ VHDL 比较是 =，赋值是 <=。C 写多了满屏 == 是编译错误，还算好抓。
  • ■ when–else 只能写在进程外（并发信号赋值），进程内必须 if–elsif 或 case。hc_sr04 注释里那句"修复：进程内用 if 替换 when"就是踩过这个坑的原话。

  • ■ 计数器不设饱和保护，上限值卡住就溢出。echo_cnt 卡高 100 ms 即越界——场地干净所以没炸。
  • ■ '1' 是 std_logic 字符，"11111111" 是 8 位向量——类型不同不能混比，case 里选错直接编译报错。
  • ■ 复位低有效是惯例（rst_n）。开发板按键按下接地，写成正有效会发现"一上电就复位"。
  • ■ 端口不接不报错——stop_req 接而未用编译器一声不吭。死线要靠 review 抓。
  • ■ case 没有 when others 兜底 = 锁存器警告。本项目的 others 给了默认直行——8 位输入 256 种组合，没列全的组合都是"保持直行"。
  • ■ 除法会综合出真除法器，单拍大位宽除法是时序重负载。常数除法优先转乘倒数+移位。
  • ■ 一个编码两种语义是 bug 温床：debug_lap 的 "11" 既表示第 3 圈又表示完成——蜂鸣器因此存在提前触发的路径。
还有一条经验整个项目大量依赖"计数器代替延时"——每个时间参数都该做成 constant 或 generic（scanner 的 STABLE_TIME 是示范，tracking_logic 里那些 750000、50000000、40000000 是反面教材）。常数集中在头部，调参才不用满文件找。

【算】CLK_PER_MM = 294 现场推一遍，并验算 echo = 117600 拍对应多少毫米。

声速 340 m/s，1 mm 往返时间 = 2 × 0.001 ÷ 340 = 5.88 μs 时钟数 = 5.88 μs × 50 拍/μs ≈ 294 拍/mm 117600 ÷ 294 = 400 mm（正是跟丢阈值 FOLLOW_TRACK_DIST）

【算】15 ms 确认、1 s 冷却、100 ms 路口锁定、20 ms 按键防抖，分别对应多少个 50 MHz 时钟周期？

50 MHz = 每毫秒 50000 拍 15 ms → 750000（BLACK_FILTER_TIME） 1 s → 50000000（COOLDOWN_MAX） 100 ms → 5000000（y_lock_cnt 装载值） 20 ms → 1000000（btn_deb_cnt 上限）

【算】38 kHz 载波的翻转计数为什么是 657？9 ms 发送窗口里大约包含多少个完整载波周期？

一个载波周期 = 50 MHz ÷ 38 kHz ≈ 1315.8 拍 方波每周期翻转 2 次 → 半周期 = 1315.8 ÷ 2 ≈ 657 拍（13.1 μs） 9 ms ÷ 26.3 μs ≈ 342 个完整周期

把 tracking_logic 里的五个 variable 全换成 signal，会发生什么？说出至少两个后果。

①"查表 → 乘比例 → 覆盖 → 输出"的流水线每步延后一拍，一次完整决策从 1 拍变 4 拍（80 ns，功能上几乎无感，但……）；②逻辑结构被迫重写：signal 版本里"先算 track 再基于它算 ratio 缩放"读不到当拍值，要么拆成多个并行进程加组合逻辑，要么上状态机分拍执行；③综合后 signal 每个都可能映射成寄存器（variable 只是组合节点），面积反而可能变大。核心考的还是那句话：变量是进程内的草稿纸，信号是进程间的传声筒。

state_lap = 3 时，debug_lap 输出什么？蜂鸣器在什么条件下会被误触发？

输出 to_unsigned(3,2) = "11"，与完成态（state_lap=4，else 分支 "11"）编码冲突。蜂鸣器触发条件是 w_lap_info="11" and w_speed_l=0 and buzzer_has_ring='0'——所以第三圈进行中只要被超声逼停（distance < 60 mm 导致速度为 0），蜂鸣器就会提前响；且 buzzer_has_ring 锁定后，真跑完时不再响。修法：加宽 debug_lap 到 3 位，或重新编码让状态 3 不输出全 1。

为什么跟车的红外启动通道可以跳过按键防抖？换成"红外也防抖 20 ms"有什么后果？

防抖的本质是时间确认——ir_sync 的接收判决已经要求低电平持续 2 ms 才输出脉冲，等于上游做过一次时间确认，再来一遍是冗余。后果层面：多等 20 ms 起步更晚（本来握手已经花 11 ms），而且防抖逻辑对单拍脉冲无效——rx_detect 只亮一拍，20 ms 计数器根本数不到 1000000 就被清零了，照抄按键防抖反而会让红外启动永远失效。

echo 引脚被干扰卡在高电平 150 ms，hc_sr04 里会发生什么？正确写法是什么？

echo_cnt 数到 range 上限 5000000 后再 +1 就是整数越界：仿真器报错停机，上板行为未定义（综合实现通常截断或回绕，距离读数跳变）。正确写法：加饱和保护（数到上限就停）并把"数满"解释为无效测量——输出一个超时标志或强制 distance 为 0，让决策端落进"跟丢"分支。顺手一提：echo 丢失（一直低）时 distance 冻结在旧值，同样需要超时兜底。
