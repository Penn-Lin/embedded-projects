00

开场：怎么把这个项目讲出去它讲的不是技术深度，是"交付意识"

30 秒 · 电梯版

团队气体检测装置里我负责采样控制单元：Nano 驱动气泵把待测气体抽过 I2C 数字流量计，自写 CRC8 逐位校验和两点线性标定，每 2 秒经蓝牙回传流量与温湿度；同时支持手机下发 ASCII 指令远程控制紫光灯、气泵并回读状态。I2C 无应答、校验失败、温湿度读空三类故障分别降级，任一路异常都不中断采样循环。

角色边界：电子控制单元的设计与实现是我；化学检测模块、手机端 App 是队友的——接口（指令集和回传格式）是我定义后跟两边对齐的（按实际讲）。
2 分钟 · STAR 版

S｜团队做气体污染物检测装置，化学侧需要"把气送进去、把数传出来"的可靠通道——采样单元是整机里第一环，坏了后面全停。T｜持续采样 + 远程控制 + 状态可确认，还要能在传感器抖一下的时候不罢工。A｜四件事：①流量计是 I2C 数字输出——实现写命令、等 1 ms、读三字节（2 字节 AD 值 + 1 字节 CRC）的完整事务，CRC 不过整帧丢弃；②AD 码值不是物理量——两点线性标定（偏移 + 斜率）换算成 L/min；③设计 ASCII 指令集（UV/PUMP/STATUS），调试时手机串口 App 手打就能验证，STATUS 让控制可确认而不只是可发送；④三类故障分层兜底：无应答、校验失败、DHT 读空各走各的降级路径，互不牵连。R｜2 秒周期稳定回传、远程控制带确认、挂上团队整机联调通过。收获一句话：比功能更早想到异常分支。

讲法提醒这个项目在面试里的定位是"工程素养证明"：投嵌入式岗时放在 PIC/FPGA 之后讲，一句话带过技术、两句话讲降级设计。面试官问"跟团队怎么协作"时它就是主角——接口我先定义、异常我先兜住，这是团队里最值钱的两种人。
01

一个 loop 两个节奏2 秒一次采样，毫秒级响应指令——millis() 分时

loop 里只有两个 if：到 2 秒了吗？到了就采一轮；蓝牙来数据了吗？来了就解析指令。两个节奏靠 millis() 时间戳切分，谁也不堵谁。

BTcontrol_v2.ino37–75 loop 骨架
void loop() {
  static unsigned long previousMillis = 0;
  const long interval = 2000;
  unsigned long currentMillis = millis();
  
  if (currentMillis - previousMillis >= interval) { ①
    previousMillis = currentMillis;
    
    float humidity = dht.readHumidity();
    float temperature = dht.readTemperature();

    if (isnan(humidity) || isnan(temperature)) { ②
      bluetooth.println("温湿度读取失败！");
    } 
    else {
      bluetooth.print("T:");
      bluetooth.print(temperature);
      ...
    }

    float flowRate = readFlowValue();
    if (flowRate >= 0) {  
      bluetooth.print("Flow:");
      bluetooth.print(flowRate, 2);  
      bluetooth.println(" L/min");
    } else {
      bluetooth.println("流量读取失败！");  ③
    }
  }
  
  if (bluetooth.available() > 0) {  ④
    String command = bluetooth.readStringUntil('\n');
    ...
  }
}
  • 经典 millis() 分时：currentMillis − previousMillis ≥ 2000——无符号差值天然免疫 millis() 的 49.7 天回绕（OLED 项目同款手法）。采样和指令响应共享同一个 loop，互不阻塞。
  • 温湿度读空先查 isnan：DHT11 失败时库返回 NaN，直接打印会输出 "nan"——对下游（手机端解析）是脏数据。失败要显式上报，不能让它混进正常数据流。
  • 失败也是信息：流量读不到时回传"流量读取失败！"而不是沉默——下游能区分"没数据"和"数据是零"。哨兵值约定：readFlowValue 失败返回 −1。
  • 指令通道永远开着：采样间隔的 2 秒里，loop 空转几百圈都在盯蓝牙——指令响应的延迟上限就是 readStringUntil 的等待（见第 07 节的诚实边界）。

02

硬件链路每个接口都是"数据量 × 实时性"的选择

五样东西挂在 Nano 上：软串口接 HC-05、I2C 接流量计、单总线接 DHT11、两根 GPIO 接继电器和紫光灯。每种通信方式都对应一类数据形态。

HC-05 蓝牙SoftwareSerial(2,4)Nano 只有一路硬件串口（要留给调试打印），蓝牙用软串口位模拟——代价见第 07 节

BTcontrol_v2.ino5–17 声明区
SoftwareSerial bluetooth(2, 4);   // RX=2, TX=4

#define DHTPIN 6
#define DHTTYPE DHT11
DHT dht(DHTPIN, DHTTYPE);

#define UV_LIGHT_TRIGGER 8  
#define RELAY_IN 10  

#define AFS01_ADDR 0x40  
#define OFFSET_FLOW 32000.0F      // 标定：零点偏移
#define SCALE_FLOW 140.0F         // 标定：斜率
const uint8_t CMD1000[2] = {0x10, 0x00};   // 读取命令
  • 两个标定常数放宏定义：32000（零点）和 140（斜率）是标定后写死的——放头部，重标定时只改这里。放函数体里就是灾难。
  • 0x10 0x00 是"读测量值"命令：按传感器协议手册发两字节命令码（Sensirion 系流量计的标准读法）。
  • 继电器脚和紫外脚在 setup 里显式拉低（33–34 行）——上电默认全关。执行器的安全态要在 pinMode 之后第一时间钉死，不然上电瞬间可能抖一下。
03

流量计驱动与标定一次完整的 I2C 事务：命令 → 等待 → 读 → 校验 → 换算

数字流量计给的不是流量，是 AD 码值。把它变成 L/min 要走五步：发读命令 → 等 1 ms → 收三字节 → CRC 校验 → 线性换算。任何一步失败都返回 −1，绝不把可疑值放行。

BTcontrol_v2.ino113–132 readFlowValue
float readFlowValue() {
  uint8_t iicRecvBuf[3];
  
  if (!i2cWriteData(CMD1000, 2)) { ①
    return -1;
  }
  
  delay(1);   ②
  
  if (!i2cReadData(iicRecvBuf, 3)) {
    return -1;
  }
  if (calcCRC8(iicRecvBuf, 2) != iicRecvBuf[2]) {  ③
    Serial.println("流量数据CRC校验失败");
    return -1;
  }
  
  uint16_t adValue = (iicRecvBuf[0] << 8) | iicRecvBuf[1];  ④
  return ((float)adValue - OFFSET_FLOW) / SCALE_FLOW;  ⑤
}
  • 写失败 = 从机没 ACK：i2cWriteData 检查 endTransmission 返回值——非零即失败（地址无应答/总线异常），立即返回 −1。
  • 1 ms 是传感器的事务转换时间：手册规定发命令后要给测量周期，立刻读会拿到旧值或乱值。
  • 三个失败出口，三个不同的原因：写失败（总线/地址）、读失败（字节数不对）、CRC 失败（内容错）——日志能区分它们，排查才有方向。
  • 大端拼字节：高字节在前。注意和 PIC 陀螺仪的小端正好相反——不同厂商不同协议，拼字节前先看手册，这是两门课换来的肌肉记忆。
  • 两点线性标定：(AD − 32000) ÷ 140。32000 是零流量对应的码值（零点偏移），140 是每 L/min 对应的码值数（斜率）——用两个已知流量点解出来的直线方程。标定方法见下面的话术框。
标定怎么讲（诚实版）面试必问"标定怎么做的"。安全的答法："按手册的出厂标定参数做了零点核对"——这两个常数与手册默认值一致（推断，按实际说）；如果真是自己拟合的，要说清用了几个已知流量点、怎么取的（比如皂膜流量计对比）。编一套没做过的流程比承认"用了厂家参数"危险十倍。
换算一例（自测用）： AD = 39000 → (39000 − 32000) ÷ 140 = 50.0 L/min AD = 32000 → 0（零流量） AD = 32740 → (32740−32000)÷140 = 5.29 L/min
04

CRC8 手写逐位12 行代码，多项式 0x31——为什么 ACK 不等于数据正确

I2C 的 ACK 只证明从机收到了字节，不证明内容没被干扰。传感器在数据后面附一个 CRC 字节——把校验的责任还给你。这 12 行就是在本地复算一遍。

BTcontrol_v2.ino152–165 calcCRC8
uint8_t calcCRC8(uint8_t *data, uint8_t num) {
  uint8_t bit, byte, crc = 0x00;      // 初值 0x00
  for (byte = 0; byte < num; byte++) {  ①
    crc ^= data[byte];                 // 字节先异或进寄存器
    for (bit = 8; bit > 0; bit--) {    // ②
      if (crc & 0x80) {                // ③
        crc = (crc << 1) ^ 0x31;       // 多项式 x^8+x^5+x^4+1
      } else {
        crc <<= 1;
      }
    }
  }
  return crc;
}
  • 外层：每个字节处理一遍。先把字节异或进 CRC 寄存器——让当前字节影响最终值。
  • 内层：8 次"移位 + 条件异或"。这就是多项式除法的位级实现：CRC 寄存器左移一位（×x），如果移出去的最高位是 1，就减（异或）多项式。
  • 0x31 = 0b0011_0001 = x⁸+x⁵+x⁴+1（最高位 x⁸ 隐含在"移出检测"里，寄存器里只留低 8 位）——Sensirion 系传感器手册规定的标准多项式。初值 0x00、无最终异或，也都按手册来。CRC 的三要素（多项式/初值/输出处理）错一个，校验永远不过。
  • 为什么它能查错：任何一个 bit 翻转，除以多项式的余数都会变——两个不同消息撞出同一个 CRC 的概率约 1/256。查单 bit 错误和相邻突发错误，8 位 CRC 是够用的最低配置。
手算一遍第一个字节（感受一下，面试可现场演示首字节）： data[0] = 0x3F，crc 初值 0x00 第一步：crc ^= 0x3F → 0x3F 然后 8 次循环（高位 1 就左移异或 0x31）： 0x3F→0x7E→0xFC→(1)0xF8^0x31=0xC9→(1)0x92^0x31=0xA3→(1)0x46^0x31=0x77→0xEE→(1)0xDC^0x31=0xED crc(0x3F) = 0xED（d 标记的为最高位是 1 需要异或的步骤）

ACK 和 CRC 到底差在哪？

ACK 是链路层的："这个字节我收到了"——从机在第九个时钟拉低 SDA。它管不了两件事：①总线上传输中被干扰后从机"收到的是错值"（它照样 ACK）；②主机这侧读到的字节被干扰。CRC 是应用层的：对内容本身算指纹。一句话——ACK 保送达，CRC 保内容，两层各管一段，谁也替代不了谁。

为什么不用查表法？速度差多少？

查表法预计算 256 项表，每字节一次查表，快 8 倍——但表要 256 字节。本项目的瓶颈是 2 秒一次的采样率，逐位版每字节 8 次循环约几微秒，毫无压力——省下 256 B RAM 在 Nano 上更值。资源换速度之前先问：要速度干嘛？

05

ASCII 指令集人可读的协议——调试成本也是设计成本

指令一共六条，全是人话：UV ON / UV OFF / PUMP ON / PUMP OFF / STATUS，外加一条兜底的用法提示。协议的可调试性是被低估的设计维度。

BTcontrol_v2.ino75–110 指令解析
  if (bluetooth.available() > 0) {
    String command = bluetooth.readStringUntil('\n');  ①
    command.trim();
    
    Serial.print("收到指令: ");
    Serial.println(command);
    
    if (command == "UV ON") {  
      digitalWrite(UV_LIGHT_TRIGGER, HIGH);  
      bluetooth.println("紫光灯已开启");
      } 
    else if (command == "UV OFF") {
      digitalWrite(UV_LIGHT_TRIGGER, LOW);   
      bluetooth.println("紫光灯已关闭");
      }
    else if (command == "PUMP ON") {
      digitalWrite(RELAY_IN, HIGH);  
      bluetooth.println("水泵已开启");
    }
    else if (command == "PUMP OFF") {
      digitalWrite(RELAY_IN, LOW);  
      bluetooth.println("水泵已关闭");
    }
    else if (command == "STATUS") {  ②
      bluetooth.print("紫光灯:");
      bluetooth.print(digitalRead(UV_LIGHT_TRIGGER) ? "开启" : "关闭");
      bluetooth.print(",水泵:");
      bluetooth.println(digitalRead(RELAY_IN) ? "开启" : "关闭");
    }
    else {  ③
      bluetooth.println("未知指令，请使用:");
      bluetooth.println("UV ON / UV OFF");
      bluetooth.println("PUMP ON / PUMP OFF");
      bluetooth.println("STATUS");
    }
  }
  • trim() 去尾部空白：手机 App 发指令常带 \r\n 或多余空格——不 trim 就永远匹配不上。跨设备协议的第一课：永远清洗输入。
  • STATUS 读的是引脚电平，不是内部变量（digitalRead）——回读的是物理事实：就算继电器没吸合、线松了，回报的就是引脚状态。语义上比"我记得我开过"诚实一层。
  • 未知指令有回音：打错字会收到用法说明而不是沉默——对面的队友不用翻文档就能纠错。协议的报错信息是给人看的，这一点二进制协议永远做不到。
为什么选 ASCII

调试阶段手机蓝牙串口 App手打指令就能测，不用先写上位机；出错时打印出来肉眼可读；队友（化学侧）也能看懂日志。代价：一条指令 7 字节 vs 二进制 2 字节——9600 bps 下多花 5 ms，完全无感。

为什么 STATUS 是刻意加的

只发不收的控制是"假设成功"——指令在路上丢了、继电器没吸合，手机端都不知道。加一条回读，控制从"发射后不管"变成"闭环确认"。这是整个协议设计里最值得讲的一句话。

什么时候该换二进制协议？

三个信号：①带宽紧张（无线低速链路）；②指令频率高（人不再参与）；③要传二进制数据（转义麻烦）。届时定长帧 + 帧头 + 长度 + CRC——和 PIC 项目接收陀螺仪的 11 字节帧是同构的。协议跟着"谁在用、多快、多可靠"走，没有银弹。

06

异常降级三层任一路挂掉，采样循环都活着——"交给别人用"的底线

三类故障三种来源：总线级的无应答、内容级的校验失败、器件级的读空。每类走自己的降级路径，互不牵连——温湿度挂了流量照采，流量挂了温湿度照发。

故障检测方式降级动作不牵连谁
I2C 从机无应答endTransmission ≠ 0
requestFrom 字节数不符		放弃本次读数，返回 −1温湿度、指令通道照常
数据内容错calcCRC8 ≠ 第三字节丢弃整帧 + 串口留日志下一轮采样自动重试
温湿度读空isnan(h) || isnan(t)单独上报"读取失败"流量采集不受影响

设计原则一句话：每个传感器的失败都是"局部事件"。如果 DHT 读空会让整个 loop 卡死或让流量也停发，那一个 ¥5 的传感器就成了整机的单点故障——廉价器件更需要被隔离，因为它更容易坏。

面试怎么讲这一节不要背表格——讲一个反事实："如果我不做分层会怎样？温湿度读空时直接 return，流量也停了，团队化学侧看到的现象是'整个采样断了'，排查要三个人一起上。做了分层之后，任何一路故障的爆炸半径只有它自己。"反事实比功能清单有说服力。

为什么不在失败时重试三次？

因为采样是周期性的——下一轮（2 秒后）本身就是天然重试。加即时重试反而拉长本轮耗时、推迟蓝牙响应。周期任务的重试策略 = "等下个周期"，事件任务才需要即时重试。这个区分是实时系统的小学功课。

07

诚实的边界"非阻塞"这三个字，这套代码其实只做到了 80%

逐行读自己的代码会看见三处真实存在的阻塞。它们在实测里都无感，但面试官真问起来，说得出这三处的人和不说的，是两种候选人。

#1 readStringUntil 最多阻塞 1 秒

BTcontrol_v2.ino76 读取指令
    String command = bluetooth.readStringUntil('\n');

Stream::readStringUntil 的默认超时是 1000 ms：available() 检查过后，只要字节流里还没出现 \n，它就守着等——这 1 秒里采样到点也不会执行。实测无感的原因：手机 App 每条指令都带换行，从第一个字节到 \n 只有几毫秒。边界场景：App 发了半条指令死机了，采样就停 1 秒。修法：bluetooth.setTimeout(50) 一行，把爆炸半径从 1 秒压到 50 ms。

#2 setup 里的 delay(2000)

BTcontrol_v2.ino20–24 上电
  Serial.begin(9600);
  bluetooth.begin(9600);
  delay(2000);            // ← 等 HC-05 模组自己起来
  bluetooth.println("蓝牙连接成功！");

等蓝牙模组进入 AT/透传模式的启动时间——上电阶段阻塞 2 秒是合理的（那时还没有任何任务在跑），列在这里只是提醒自己区分"上电等待"和"运行等待"：前者可接受，后者才要 millis() 化。

#3 DHT11 的库函数本身是阻塞的

自测 6 题一道动笔算，一道动嘴讲

答案默认折叠。先写下来再展开。

【算】AD 读数 33400，OFFSET=32000、SCALE=140，流量是多少？读数 31000 呢？后者说明什么？

(33400 − 32000) ÷ 140 = 10.0 L/min (31000 − 32000) ÷ 140 = −7.14 L/min 负流量物理上不可能 → 零点偏了或读数错——线性外推到量程外就是会出这种"数学正确、物理荒谬"的值， 换算后要加量程合理性检查（本版没加，如实交代）

CRC8 的多项式 0x31 对应什么？三要素是什么？错一个会怎样？

0x31 = 0b00110001 = x⁸+x⁵+x⁴+1（Sensirion 标准）。三要素：多项式、初值（本实现 0x00）、输出处理（无最终异或）。任何一项与手册不一致，算出的 CRC 永远对不上——表现为"校验永远失败"，而总线通信其实完全正常。排查这种问题先对三要素，别动时序。

readStringUntil('\n') 在什么情况下阻塞？阻塞多久？两个修法？

available() 有字节但流里迟迟等不到 \n 时，最多等默认超时 1000 ms——期间整个 loop 停转（采样、其他指令全停）。修法一：bluetooth.setTimeout(50) 把爆炸半径压到 50 ms；修法二（彻底）：非阻塞状态机逐字节拼帧——收到 \n 才开始解析，其余时间立即返回。

millis() 分时的差值写法为什么回绕安全？如果写成 millis() >= previousMillis + 2000 呢？

(uint32_t)(now − last) 利用模 2³² 减法：翻转后差值依然等于真实经过的毫秒数。而 now >= last + 2000 里 last + 2000 本身可能溢出回绕——比较的基准变成了一个错值，在翻转点附近会误触发或永不触发。计时比较一律写差值形式（与 PIC 项目易错点同源）。

三类故障的检测点和降级动作分别是什么？"互不牵连"在代码结构上靠什么保证？

①无应答：endTransmission 返回值 / requestFrom 字节数 → 放弃本轮返回 −1；②内容错：calcCRC8 ≠ 第三字节 → 丢帧 + 日志；③DHT 读空：isnan → 单独上报。结构保证：每个故障的处理都在自己的 if 分支内闭合，没有一条路径会因为任何传感器失败而 return 出 loop——采样循环的骨架对故障"免疫"。
